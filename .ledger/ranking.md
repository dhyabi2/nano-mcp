# Ranking: 50 brainstormed ideas → the invention for nano-mcp

Goal: an MCP server + small SDK so any AI agent can hold XNO and pay per API call in Nano,
transacting through the public node rpc.nano.to. Ideas generated by the Methodology-Tree engine
(50/50 with answers) from the 10 benchmark features in benchmark-features.json.

## Mechanism clusters that survived the screen

Reading all 50, the ideas reduce to a few distinct mechanisms:

A. **One-time per-request derived payment address** (ideas 5, 6, 15, 16, 18, 41, 43, 23): the
   server derives a unique destination address per request (HMAC/HKDF from a server master key +
   request_id), publishes {price, address, request_id}; the agent sends the exact amount there;
   the server watches that address's on-chain account_history and approves the call when the
   matching send arrives. No memo needed (Nano blocks have no memo) — the address IS the memo,
   and it is deterministic and reusable per request id only.
B. **Signed-block voucher** (8, 46, 47, 38, 39, 48): the agent signs a send block (fee to server)
   but first hands the *raw signed block* to the server; the server verifies signature+amount
   then broadcasts it. Fast but has a sign-before-broadcast double-spend window that must be
   handled (server must broadcast or verify on-chain before granting).
C. **Credit / stake / token-bucket / prepaid** (14, 19, 32, 33, 34, 35, 49): deposit once,
   deduct per call off-chain. Good for rate/intensity control but reintroduces off-chain state
   for the settlement guarantee.
D. **Proof-of-work offload** (27, 26, 3): sign locally, get PoW from a work-for-hire HTTP service
   (rpc.nano.to work_generate) so a lightweight agent never does CPU/GPU mining.
E. **Verification robustness** (7): ask several independent RPC nodes for the same block.

## Winner: fuse A (core) + D (infrastructure) + per-request idempotency

nano-mcp = self-custody Nano **SDK** + **MCP server** where:

- SDK: derive wallet from a seed (blake2b-256 account id → ed25519-blake2b sign key → nano_ address),
  read balance/history via rpc.nano.to, and *send* by signing the block locally and getting PoW
  from rpc.nano.to `work_generate`, then broadcasting via rpc.nano.to `process`.
- Pay-per-call (the invention): the MCP server derives a **one-time payment address per request**
  from a server master key + request_id, returns a quote {price_raw, address, request_id}; the
  agent's SDK sends exactly `price_raw` to that address; the server watches that address's
  account_history and approves the tool call once the matching on-chain send is confirmed.

Why this beats the x402/USDC incumbent: no trusted interposed verifier — the service reads the
public chain it transacts on; no issuer to freeze funds; no bridge. Feeless + instant make truly
per-call (even per-micro-call) billing economic, so no batching (the gap F1 explored).
Because the destination address is per-request and one-time, one payment authorizes exactly one
call (F9 replay-safety) and the request↔payment association needs no memo (F2).

## Rejected gimmicks (explicit, with reason)

- 24 Merkle-batched one-tx-for-N-calls — contradicts the feeless-per-call advantage AND adds a
  build-time merkle layer; no value for MVP.
- 29 2-of-2 threshold MPC Ed25519 — heavy, fragile, needs a delegate; pure over-engineering.
- 14 Hawkes-process burst prediction — speculative complexity; nothing to predict at MVP scale.
- 4 / 30 / 31 / 34 PID / AIMD pricing — pricing optimizer, not the mechanism; nothing to prove
  about per-call billing. Defer entirely.
- 9 Bloom-filter + VRF probabilistic verification — probabilistic access control on money; wrong
  default, must be deterministic.
- 44 hash-chain pre-shared H0 — proves order, not meaning (ledger lesson); adds a shared-secret
  setup that a one-time address avoids.
- 22 request_faucet tool — would solicit funds from third parties, against workspace money rules.
- 21 challenge-response TTL — workable but needs stateful TTL bookkeeping; one-time address is simpler.

The invention — a feeless, self-sovereign, per-call Nano pay-gate where the chain itself is the
verifier — is genuinely new relative to the stablecoin/x402 MCP servers: it removes the trusted
verifier and makes micro per-call billing economically the *simplest* case.
