The wheel was then installed into a **brand-new venv with no dev extras** and driven through the

`nano_sdk.block`. All correct. The 5 `network` tests were not run: they need a live node and a key

The 09-24 and 09-26 passes read `nano_sdk/` line by line and property-tested the codecs. Repeating
that would have found nothing, so this run drove `nano_to_raw` across every malformed shape an agent
could hand it, and drove the **wallet's daily cap the way an agent loop actually runs** — one process
per run. The last of those is the finding.

## Found — nothing fixed, because all of it is money or key code

Nothing in this note is changed. The standing instruction for these audits does not merge money code,
and `wallet.py` is the send path.

**1. The daily cap does not survive the process, so "0.01 XNO per day" is not what it enforces.**
`wallet.py:5` states the money rule — "outbound total from any wallet is at most 0.01 XNO per day" —
and then: *"This module enforces both before anything is signed or published."* It enforces the
balance check always, and the cap **only within one `Wallet` object's lifetime**. `_spend` is an
instance dict (`wallet.py:57`); nothing reads or writes it to disk. A fresh `Wallet` starts at zero
spent. Driven against a stub node that always reports a funded account and accepts every block, same
seed, same UTC day:

```
run 1: sent 0.01 XNO;  second send in the SAME process -> DailyCapExceeded   (the cap works in-process)
run 2: sent 0.01 XNO;  second send in the SAME process -> DailyCapExceeded
run 3: sent 0.01 XNO;  ...
run 4: sent 0.01 XNO;
run 5: sent 0.01 XNO;
TOTAL across 5 processes, one seed, one UTC day: 0.05 XNO
documented maximum for that day:                0.01 XNO
```

Five times the cap, with no guard tripped, and the agents this SDK is written for run exactly that
way — a loop that starts a process per run. This is a different fault from the UTC-bucket note the
09-24, 09-25 and 09-26 passes carried forward (that one is about *when* the bucket resets; this one is
that there is no bucket across processes at all). Both are still open. A fix means persisting the
spend beside the wallet and reserving before signing, which is money code and a design decision.

**2. `nano_to_raw` reads `"1_0"` as ten.** Python's `Decimal` accepts `_` as a digit separator, so
`units.py:31` takes it:

```
nano_to_raw("1_0")  -> 10000000000000000000000000000000   # 10 XNO
nano_to_raw("1")    ->  1000000000000000000000000000000   #  1 XNO
```

The repo's own stated threat model is a model-supplied amount (`test_repo_tree.py:88` turns on
"a model-supplied `nan` amount"). Under it, a malformed amount string is silently reinterpreted at
ten times its digits rather than refused. `" 1 "` and `"\t1\n"` are likewise accepted; those do not
change the magnitude. Left alone deliberately: this is the amount an agent is about to send, and
tightening it is the owner's call, not an auditor's.

**3. A bad account index escapes the key path as `OverflowError`.** `crypto.derive_private_key`
documents `ValueError` for the seed and validates it, then does
`int(index).to_bytes(4, "big")` (`crypto.py:49`) with no check on `index`. `Wallet.account(index)` and
`Wallet.send(..., index=...)` pass it straight through, so `index=-1` or `index=2**32` raises
`OverflowError`, which is not a `ValueError` and is not documented. Nano's index is a uint32; the
range is knowable. Same contract-violation shape the 09-24 and 09-26b passes fixed twice on this
module (an escaping `AssertionError`, then an escaping `KeyError`) — a third route was still open.

**4. Every installer pulls the whole MCP server stack for code that does not exist.**
`pyproject.toml` declares `mcp>=1.0` as a hard runtime dependency. Nothing in the tree imports it —
there is no `nano_mcp/` package, only `nano_sdk/`, and the README marks the MCP server as "later
blocks". Confirmed: `grep -rn "import mcp" nano_sdk/ tests/` finds nothing, and the built wheel's
`top_level.txt` is `nano_sdk` alone. So `pip install nano-mcp` drags in `mcp`, `starlette`,
`uvicorn`, `sse-starlette`, `pydantic` and their tree to get an SDK that needs `httpx` and
`ed25519-blake2b` only. Moving it to an optional extra would change the install contract, which is a
packaging decision rather than a fix, so it is reported and not touched.

## Checked and clean

- The address codec: `nano_`/`xrb_` round-trips, the `\Z` anchor still refuses a trailing newline
  (09-26b's fix holds), the 256-bit width check, checksum mismatch refused.
- `nano_to_raw` raises `ValueError` and nothing else across 27 malformed inputs — `""`, `"abc"`,
  `"nan"`, `"snan"`, `"inf"`, `"1,5"`, `"0x10"`, `"1.2.3"`, `None`, `[]`, `{}`, `b"1"`, `"1e-31"` and
  the rest. The 09-26 contract fix holds.
- `nano_str(0)` is `"0"`, not `""` — the strip-to-empty case is handled.
- `RpcClient.call` still refuses a non-200, a 200 that is not JSON, a JSON non-object and an `error`
  key, all as `RpcError`.
- `repr(Wallet)` does not print the seed; `repr(Account)` does not print the private key.
- No build output tracked; `git check-ignore` answers for `build/` and `dist/`.
- Packaging: the build backend resolves the package list from the repo root, and discovery selects
  `nano_sdk` while excluding `audits` and `tests`.

## Secrets

Clean. No seed, key or credential in the tree. Every 64-hex literal in `tests/` is a documented
docs.nano.org test vector or an all-zero seed used as a fixture.
