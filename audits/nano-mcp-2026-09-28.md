# nano-mcp — code audit, 2026-09-28

Scope: the tree at `88756a3` (`main`). Baseline in a clean virtualenv, before any change:

```
$ pip install -e ".[dev]"                  # succeeds
$ python -m pytest -m "not network" -q
64 passed, 5 deselected
$ python -m build --wheel
Successfully built nano_mcp-0.1.0-py3-none-any.whl
```

The 09-26 `\Z` anchor fix is on `main` and holds. The earlier runs read `crypto.py` and `units.py`
line by line and drove the conversions and the address codec with random inputs; repeating that
would have found nothing. This run instead drove **every public entry point with the wrong TYPE and
the wrong LENGTH of argument** — the cases a caller reaches not by malice but by reading a key or an
address out of a file, a JSON body or a config. Both findings below came out of that.

## Found

**`public_key` accepted a 64-byte input and echoed 32 of those bytes back as the "public key",
producing a valid-looking address that no private key can sign for.** `crypto.py:52` had no length
check at all; it handed its argument straight to `ed25519_blake2b.SigningKey`. That constructor
refuses most wrong lengths — 0, 16, 31, 33 all raise — but it also accepts the 64-byte
`seed || verifying key` form, in which **bytes 32:64 are taken as the verifying key verbatim**. So:

```
hex_key = "00"*31 + "01"
public_key(bytes.fromhex(hex_key)).hex()  -> c969ec348895a49e21824e10e6b829edea50ccc26a83ce8986a3b95d12576058
public_key(hex_key).hex()                 -> c969ec...  (same; the str branch decodes it)
public_key(hex_key.encode()).hex()        -> 3030303030303030303030303030303030303030303030303030303030303031
                                             ^ ACCEPTED - and that is just the input's own tail
  address_from_public_key(that)           -> nano_1e3i81r51e3i81r51e3i81r51e3i81r51e3i81r51e3i81r51e3juqsa5t4t
```

That address is well-formed and its checksum verifies, so `validate_address` returns `True` and
nothing downstream objects. **There is no private key behind it**: the bytes were never a public key,
they were ASCII text. XNO paid to it is unspendable by anyone, permanently.

The two inputs that produce it are ordinary, not exotic — `hex_key.encode()`, and
`open(keyfile, "rb").read()` for a key file holding 64 hex characters. The sibling function
`derive_private_key` guards exactly this slip already (`ValueError: seed must be 32 bytes (64 hex
chars)`), which is what makes the gap in `public_key` an inconsistency rather than a policy:

```
derive_private_key(hex_key.encode())  -> ValueError: seed must be 32 bytes (64 hex chars)
public_key(hex_key.encode())          -> (a wrong key, silently)
```

**Fixed** by checking `len(private_key) != 32` after the hex-string branch and raising `ValueError`,
the same shape and message as `derive_private_key`. Nothing else changed. The change can only
*refuse* more: no caller in the repository passes 64 bytes (the two call sites are
`tests/test_crypto.py:52`, a 64-hex *string*, and `crypto.py:120`, a 32-byte key), and both accepted
forms are pinned by the new tests.

Proved both directions. Against the unfixed `crypto.py`:

```
FAILED tests/test_crypto.py::test_the_ascii_bytes_of_a_hex_key_are_refused_not_silently_accepted
FAILED tests/test_crypto.py::test_public_key_accepts_exactly_32_bytes_and_refuses_every_other_length
E           Failed: DID NOT RAISE ValueError
```

With the fix, same venv: **66 passed, 5 deselected** (64 before), and `python -m build --wheel` still
succeeds with `nano_sdk` as the only shipped package.

**Not merged.** `crypto.py` is the key path, which the standing instruction for these runs excludes
from self-merging, so this is a pull request left open for a person. The 09-26 run left a `crypto.py`
fix open for the same reason.

## Found, not fixed — for a person

**`validate_address` raises `TypeError` on any non-string input, though it is documented to return a
bool — and `Wallet.send` guards its destination through it.** `crypto.py:76` calls
`ADDRESS_RE.match(address)` before anything narrows the type:

```
validate_address(None)          -> TypeError: expected string or bytes-like object, got 'NoneType'
validate_address(addr.encode()) -> TypeError: cannot use a string pattern on a bytes-like object
validate_address(12345)         -> TypeError: expected string or bytes-like object, got 'int'
public_key_from_address(None)   -> TypeError   (documented: "Raises ValueError if ... malformed")
```

`validate_address` catches only `ValueError`, so the `TypeError` escapes a function whose whole
signature is `-> bool`. `wallet.py:130` is the consequence that matters: a caller whose `destination`
came from a JSON body or a config where the key was absent passes `None`, and gets
`TypeError: expected string or bytes-like object` instead of the wallet's own
`"destination is not a valid nano_ address"` — and cannot catch it with the `except ValueError` the
docstring tells them to write.

This is the **third** route to the same contract violation in this one function: 09-24 fixed an
escaping `AssertionError`, 09-26 fixed an escaping `KeyError('\n')`, and a wrong *type* still gets
through. It is left for a person only because it is a second change to the key path in the same run
and the fix above should be reviewed on its own; the fix itself is one `isinstance` check.

**`Wallet.send` validates the node's `work_generate` answer with a bare `assert`** (`wallet.py:147`).
`python -O` strips assertions, so under `-O` a node answer without a usable `work` key stops being
refused there: `work = gen["work"]` raises `KeyError`, and a non-string `work` is carried into the
signed block instead of being rejected. Money code, deliberately untouched — but an `assert` is the
wrong tool for validating a remote answer, and the repository ships no `-O` warning.

**`pyproject.toml` declares a hard runtime dependency on `mcp>=1.0` that nothing in the distribution
imports.** The wheel ships `nano_sdk` and nothing else; `nano_mcp/` does not exist (README:19 marks it
"later blocks"); `grep -rn "import mcp\|from mcp" nano_sdk/` finds nothing. So every installer pulls
the whole MCP SDK and its transitive tree for code that never uses it. Whether that dependency is
anticipatory or a leftover is a release decision, so it was not touched.

**Still open from earlier runs, all money or release decisions:** no `LICENSE` and no `license` field
while the public sibling is MIT (a public repo with no licence grants a reader no rights at all); two
repositories publishing `nano-mcp` `0.1.0` with different code; `wallet.py:138`
`info.get("representative", self.representative)` vs the sibling's `or` form, which differ when the
node returns an empty value; and the daily cap being a UTC calendar-day bucket rather than the rolling
24 hours the docstring promises. Four audits have now reported the cap.

**The same `public_key` gap is live in the sibling `dhyabi2/nano-mcp-public`**, which carries its own
copy of `crypto.py`. It is raised there separately.

## Checked and clean

- **Type and length fuzzing of the whole public surface.** `nano_to_raw` honours its "ValueError and
  nothing else" contract for `None`, `bytes`, `list`, `dict` and `bool`. `raw_to_nano` rejects
  non-`int` with `TypeError` as documented. `nano_str` is correct for `0` and for negative raw.
  `derive_private_key` refuses every seed length but 32. Only the two address functions above break
  their stated contracts.
- **`client.py`.** `RpcError` covers the four cases its docstring claims — non-200, non-JSON body,
  non-object JSON, and an `error` key — and each raises before a caller can index the result. No
  credential reaches a log: the API key goes into a header, never a URL or a message.
- **`block.py`.** `_block_bytes` length- and range-checks all six fields before hashing, and
  `build_send_block` re-checks `previous` and `private_key` at 32 bytes. The field order matches the
  module docstring and the docs.nano.org test vectors in `tests/test_block.py`.
- **No secrets in the tree.** The 64-hex-shaped lines are the published `docs.nano.org` all-but-one-
  zero seed vectors and keys derived from it, plus two public block hashes in `.ledger/ledger.json`.
  No `.env`, `.pem`, `.key` or token shape is tracked, and nothing of that kind is in the history a
  shallow clone carries.
- **Packaging.** `pip install -e ".[dev]"` and `python -m build --wheel` both succeed; the wheel holds
  `nano_sdk` only — `audits/` gaining a fifth file did not break the `packages.find` fix.
- **The README** contains no links, so it has nothing that can 404.
- `nano-mcp` is still not on PyPI, so no published artefact carries any of this.
