# nano-mcp — audit 2026-10-08

Through the lens: *can an agent pay, or get paid, in XNO with this today without being hurt?*

Base: `ef362db` (`facilitator: ask for json_block, so the payee can actually be read (#19)`).
Installed from the declared dependencies (`pip install -e ".[dev]"`), suite green before any
change: **198 passed, 6 skipped, 6 deselected**.

## Found and fixed (this PR)

**`verify_payment` believed the payer's own numbers** — `nano_mcp/server.py:129`,
`nano_mcp/service.py:204`. `verify_payment` is an MCP *tool*, and in the pay-per-call flow the
agent calling it is the one that owes the money: the `quote` and `quote_usd` docstrings
(`server.py:110`, `server.py:122`) tell a buyer to pay `price_raw` and "then call
verify_payment(request_id, price_raw)". Two of its arguments were taken on trust, and the
quoted price was never recorded anywhere — `store.py`'s schema held `approvals` and
`quote_expiry` only, and `amount_raw` was written at claim time from whatever the caller passed.

Driven through the real `MCPServer` tool surface against a node that shows only what the payer
really sent:

| | what the payer did | what it got |
|---|---|---|
| A | `verify_payment(rid, amount, require_onchain=False)` | `status: approved`, `tx_hash: "simulated"` — and the node was asked **nothing at all** (`asked == []`) |
| B | quoted 1 XNO (`10**30` raw), sent **1 raw**, called `verify_payment(rid, "1")` | `status: approved` with a real tx hash — a 1 XNO call bought for `10**-30` XNO |

A third path made B worse: `pay_and_call` (`server.py:139`) re-quotes at an amount **its own
caller names**, so a payer could quote itself down and then be verified against the lower number.

The fix adds refusals only:

* `store.record_quote_price()` / `quote_price()` record what *this server* quoted, as TEXT —
  SQLite's INTEGER is 64-bit and overflows above ~1.8e19 raw, which is under 0.00002 XNO. The
  record **never lowers**, so `pay_and_call` cannot walk the floor back down.
* `service.verify_payment()` checks the **higher** of the amount its caller names and the amount
  this server quoted. It only ever rises: a caller demanding more than was quoted still gets the
  stricter check it asked for, and a `request_id` this server never quoted for (the `get_address`
  path) is unchanged.
* The `verify_payment` **tool** no longer takes `require_onchain`. The service method keeps it as
  an in-process test seam; it is simply not reachable from the surface a payer talks to.

No amount, destination, rounding or key path is touched, and nothing that was refused before is
accepted now.

**Evidence.** 7 new tests. With `tests/` kept and `nano_mcp/` alone reverted to `main`:
**4 failed, 3 passed** — the 3 are controls that must hold either way. With the fix: **7 passed**,
full suite **205 passed, 6 skipped, 6 deselected**. Both guards mutation-checked: `if False:` on
the floor in `service.py` fails 3 tests; a plain overwrite instead of the non-lowering `max` in
`store.py` fails `test_pay_and_call_cannot_quote_the_payer_back_down`. The tree was restored
byte-for-byte after each and the full suite re-run.

## Found, NOT fixed here — needs the owner (separate PR)

**`usd_to_xno_raw` quotes an amount rounded at the 28th significant digit** —
`nano_mcp/pricing.py:92`. `price_usd / rate_xno_usd`, then `* RAW_PER_NANO`, both run in the
**process-global** `Decimal` context, whose `prec` defaults to 28 while a raw amount reaches 39
digits. Nothing in the repository ever sets it. Measured against an exact integer ceiling:

| price USD | rate | quoted | exact ceiling | error |
|---|---|---|---|---|
| 1.00 | 0.34 | `2941176470588235294117647059000` | `…058824` | **+176 raw** |
| 1.00 | 0.33 | `3030303030303030303030303030000` | `…030304` | **−304 raw** |
| 0.05 | 0.9876543 | `50625001075781272860352048280` | `…283` | **−3 raw** |

The negative rows contradict the function's own docstring — "rounding UP so the seller never
under-receives". Worse, the quote depends on the **host program's** `Decimal` context: the same
price and rate give `…059000` at `prec=28` and `…058824` at `prec=40`. `nano_mcp` is a library an
agent imports, and Nano has no memo, so the amount *is* the tag — a buyer that recomputes the
price under a different context pays a number the seller will not match.

Same defect class as the one already fixed in `nano-mcp-public`'s `usd_to_xno_raw` and open in
`langchain-vend#5` and `gpt-researcher-x402-retriever#8`. The correct fix (exact integer ceiling
division) **changes a quoted amount**, so it is past `TIER0.md`'s "only adds a refusal" grant and
is not merged by a routine. Economically the error is at most a few hundred raw (~`10**-28` XNO);
the reason to fix it is correctness and host-independence, not value.

## Checked and clean

* **Integer raw throughout the money path.** `nano_sdk/units.py` converts by rebuilding the
  Decimal exponent (`_rescale`) rather than multiplying by `10**30`, so it is exact and
  context-free; `nano_to_raw` refuses >30 decimal places, non-finite and negative amounts, and
  normalises `InvalidOperation` to `ValueError`. No float appears on an amount anywhere.
* **The two defects fixed in the published twin on 2026-10-08 are not present here.**
  `Wallet.seed` is `field(repr=False)` and `Account.__repr__` withholds the private key
  (`crypto.py:139`), so no traceback or `pytest -l` carries a seed; and `check_send`
  (`wallet.py:86`) excludes `bool` explicitly before anything is signed, so `send(dest, True)`
  raises instead of publishing a real send of 1 raw.
* **`Wallet.send`** reads `balance` and `frontier` from a single `account_info` answer — one point
  in time, so it does not pair a tip frontier with a confirmed balance the way
  `nano-wallet-xno#4` describes. Guards (type, positive, balance, daily cap) all run before
  anything is signed or published.
* **Exactly-once approval.** `ApprovalStore.claim` is an atomic `INSERT … PRIMARY KEY`, so a
  replay returns `spent` across restarts and under concurrency; reads and writes serialise on one
  lock, as the comment in `_row` explains.
* **Unconfigured, the server refuses.** `MasterSecretNotConfigured` rather than a secret generated
  on the fly, so no address is ever minted whose key dies with the process.
* **Dollar-quote TTL** is enforced on the verify side (`service.py:197`), not merely advertised.
* **No secret in the tree.** The master secret is read from `NANO_PAYMENT_MASTER_SECRET`; grep
  over the tree and `git log -p` found no seed, key or token committed.
* Dependency floor (`mcp>=2.0.0`) is held by a test, and the declaration matches the module the
  server actually imports.

## Could not verify

* **No live node and no live payment.** This environment's network policy reaches neither
  `rpc.nano.to` nor the three price APIs, so the 6 network tests are deselected and every result
  above is measured against the repository's stubs and recorded shapes. No XNO moved.
* **Whether any seller has been underpaid in practice** through either hole is not knowable from
  here; both are reachable from the tool surface by construction, which is what is shown.
* `_onchain_paid`'s `etype == "send" and entry["account"] == account.address` branch
  (`service.py:160`) looks unreachable against a real node, which reports the *counterparty* in
  `account_history`'s `account` field — so it would require a self-send. Left alone: not
  demonstrably live, and changing it is not a refusal.
