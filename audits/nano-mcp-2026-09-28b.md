# nano-mcp — code audit, 2026-09-28

Scope: the tree at `88756a3` (`main`). Baseline in a clean virtualenv, before any change:

```
$ pip install -e ".[dev]"                  # succeeds
$ python -m pytest -m "not network" -q
64 passed, 5 deselected
$ python -m build                          # wheel AND sdist this time
Successfully built nano_mcp-0.1.0.tar.gz and nano_mcp-0.1.0-py3-none-any.whl
```

Earlier runs read `nano_sdk/` line by line (09-24) and fuzzed the pure functions against their
docstrings (09-26). This run took the third angle left: it drove every **exported** function with the
shapes a caller actually holds — a key read from a file, a key whose leading zero byte was trimmed, an
address with whitespace on it — and checked each answer against the library's *own* validator rather
than against the docstring. One defect came out of that, on the one function of the pair that had never
been length-checked. The 5 `network`-marked tests were not run: they need a live node and
`NANO_RPC_KEY`, which this sandbox has neither of.

## Found and fixed

**`address_from_public_key` accepted a key of any length and silently returned a broken address.**
`crypto.py:64` documents "a 32-byte public key" and checked nothing. `_b32_fixedwidth(value, 52)`
writes exactly 52 characters whatever the integer is, so a longer key loses its high bytes and a
shorter one is zero-extended — while `checksum()` is taken over the bytes *as given*. What comes back
is 65 characters long, starts with `nano_`, contains nothing but alphabet characters, and is not an
address:

```
address_from_public_key(b"\x11"*33)   -> 'nano_46aj46aj…ooceg87x'      accepted
validate_address(that)                 -> False
address_from_public_key(b"")           -> 'nano_11111111…7rmwcs5x'      accepted
address_from_public_key(hexkey.encode()) -> 'nano_46aj46aj…dpjm8zb5'    accepted
```

The failure is that it is a *value*, not an exception. It reads as an address everywhere a string is
displayed, pasted into an invoice, written into a manifest or logged, and the only thing that objects is
a checksum check nobody performs on their own encoder's output — so the error surfaces at the far end,
at the node or at whoever was asked to pay, with nothing pointing back at the call that made it.

Neither input is exotic. **64 bytes is what `open(keyfile, "rb").read()` returns for a file holding 64
hex characters**, and it is the length `ed25519_blake2b` itself also accepts — the same slip that the
open pull request #10 closes on the sibling function. **31 bytes is the ordinary result of trimming
leading zero bytes off an integer.** The two functions on either side of this one guard exactly this:

```
derive_private_key(hexkey.encode())      -> ValueError: seed must be 32 bytes (64 hex chars)
public_key(hexkey.encode())              -> ValueError (with #10) / a wrong key (without it)
address_from_public_key(hexkey.encode()) -> an address-shaped string, silently   <- this repository
```

**Fixed** with one length check at the top of the function, raising `ValueError` with the same message
shape as `derive_private_key`. Nothing else is touched.

It can only *refuse* more. The one internal call site is `derive_account` (`crypto.py:121`), which
passes a 32-byte key, and the second new test pins that no address the library produces changes:
`DOCS_PUB_EXPAND` still encodes to the documented example address, and 25 derived accounts still encode
to the address they were built with — as `bytes`, `bytearray` and `memoryview`, so the check does not
narrow the accepted types.

from self-merging, and the two tests that would prove it in CI are the offline ones — the live-node

and will conflict there textually. Neither touches the other's function (`address_from_public_key` vs
`public_key`), so the resolution is keep-both, in either order.

## Found, not fixed — for a person

- **Still no licence.** No `LICENSE` file, no `license` field in `pyproject.toml`, while the public
  sibling `dhyabi2/nano-mcp-public` carries both and says MIT. A public repository with no licence is
  "all rights reserved": a stranger who follows the README has no granted right to use it. Third audit
  to report it; it is the owner's declaration to make, not an auditor's.
- **Two repositories still publish `nano-mcp` version `0.1.0` with different code.** Unchanged from
  09-26. Both `pyproject.toml` files say `name = "nano-mcp"`, `version = "0.1.0"`; this tree has no
  `nano_mcp/` server package and no `build_receive_block` / `Wallet.receive`. `nano-mcp` is still not on
  PyPI (`pypi.org/pypi/nano-mcp/json` → **404**), so no published artefact carries the ambiguity yet —
  which is exactly the window in which to decide which repository is the distribution.
- **The README's first line promises an MCP server this repository does not contain.** "An **MCP
  server + SDK**", and `pyproject.toml` requires `mcp>=1.0` — but no file in the tree imports `mcp`, and
  the repo-layout section marks `nano_mcp/` "(later blocks)". So every installer pulls the MCP SDK for
  code that is not here. Which half ships from where is the same release decision as above, so the text
  was left alone rather than rewritten under a guess.
- **The money-path drift, reported and not touched.** `wallet.py:138` reads
  `info.get("representative", self.representative)` where the sibling reads
  `info.get("representative") or self.representative`; a node answering with an empty value makes this
  version raise and the sibling fall back.
- **Unchanged from 09-24, 09-25 and 09-26: the daily cap is a UTC calendar-day bucket, not the rolling
  24 hours the docstring promises.** `Wallet` says "at most 0.01 XNO per day"; `_today()` keys spend on
  `int(time.time()) // 86400`, so the full cap can be spent at 23:59 UTC and again at 00:01. Money code
  — it needs the owner's call on which behaviour is intended. Fourth audit to report it.
- **`wallet.py:147` guards `work_generate`'s answer with a bare `assert`.** Under `python -O` the
  assert is stripped and the next line raises `KeyError` instead. Money path; reported, not touched.

## Checked and clean

- **No secrets, in the tree or in the history a shallow clone carries.** 13 lines are 64-hex shaped:
  they are the published `docs.nano.org` vectors (the all-but-one-zero seed, the keys and block hashes
  derived from it) in `tests/test_block.py` and `tests/test_crypto.py`, plus one line of pytest output
  quoted in `.ledger/ledger.json`. No `.env`, `.pem` or `.key` is tracked; nothing token-shaped; the
  only files matching *wallet*/*seed* are `nano_sdk/wallet.py` and its test.
- **Packaging, both artefacts.** `pip install -e ".[dev]"` succeeds; `python -m build` produces wheel
  **and sdist**. The wheel ships `nano_sdk` and the `dist-info` and nothing else — `audits/` and
  `tests/` stay out, so the 09-25 `packages.find` fix still holds with a fifth audit file added. The
  sdist ships the tests, and `test_packaging.py` runs correctly from it (`test_repo_tree.py` skips
  without a `.git`, by design).
- **`RpcClient.call`'s error surface.** Every non-node answer raises `RpcError`: non-200, a body that is
  not JSON, a body that is JSON but not an object, and an object carrying `error`. Re-checked against
  the six shapes `test_client_offline.py` pins plus an empty object and a `null` body. A transport
  failure (`httpx.ConnectError`, `ReadTimeout`) is *not* wrapped — that is not "an answer", so it is
  consistent with the docstring, but a caller that only catches `RpcError` will still see httpx.
- **The address decoder, after the newline fix.** Whitespace on either side, upper case, a wrong
  prefix, a dropped character and a flipped last character are all refused; `xrb_` still decodes; the
  `pub_n >= 1 << 256` guard is unreachable given the `[13]` first character the regex requires, and
  harmless.
- **Units.** Re-checked the shapes a model-supplied amount arrives in: `"nan"`/`"inf"` raise
  `ValueError`, `"1e3"`, `".5"`, `"+1"`, `" 12 "` and `"-0"` parse as expected, `"1e-40"` is refused for
  precision, `nano_str(0)` is `"0"` and not an empty string, and `raw_to_nano` refuses a float.
