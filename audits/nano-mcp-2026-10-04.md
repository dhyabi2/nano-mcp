# nano-mcp — audit 2026-10-04

Lens: can an agent pay — or get paid — per tool call in XNO with this, today, without being
hurt? Previous audits: 2026-09-28, 2026-09-28b, 2026-09-29, 2026-09-30, 2026-10-02. This run
concentrated on the x402 facilitator, which is the half that decides whether a seller has been
paid, and which the previous audits had read less closely than the wallet and crypto paths.

## Checked

- `pip install -e ".[dev]"` and `python -m pytest -q -m "not network"` — the commands CI runs.
  **184 passed / 6 skipped** before the change, **193 passed / 6 skipped** after. Plus CI's
  `server_from_env` import smoke step.
- `nano_mcp/facilitator.py` end to end: `normalize_block_info`, `NormalizedBlock.is_send`,
  `verify_block_on_independent_endpoints`, and both callers (`verify` at `:376`,
  `settle` at `:421`).
- **A real `block_info` reply, fetched live from `rpc.nano.to`**, for a real confirmed send
  block and a real receive block, in exactly the shape `facilitator.py` asks for them.
- `nano_sdk/units.py` in full, and a float search across `nano_mcp/` and `nano_sdk/`.
- `pricing.py`, `evidence.py`, `store.py` and `paidtool.py` for a second site with the same
  defect (there is none; `facilitator.py:234` was the only one).

## Found and fixed — a seller could be told it was paid when the XNO went elsewhere

**`verify_block_on_independent_endpoints` skipped the payee check on every reply a real Nano
node returns.** Two faults compounding, and the second hid the first.

**1. `normalize_block_info` did not read the field a real send block carries its payee in.**
It built `destination` from `contents.destination`, `link_as_account`, `destination` and `link`
(`facilitator.py:134-140`). A real node returns a **state** block: the payee is in
`contents.link_as_account`, and `contents.destination` does not exist — that field belongs to
the pre-state send blocks nobody has been able to create since 2018. The other three were read
from the **top level**, where a node puts none of them. Captured live from `rpc.nano.to`, block
`64AD5A5C...FEDF`:

```
  subtype                  'send'              <- top level
  contents.type            'state'
  contents.link_as_account 'nano_1natrium...'  <- the payee, and the only place it appears
  contents.destination     ABSENT
```

So `destination` came back as `""` for every real block.

**2. An unreadable payee was then defaulted to the expected one.** `facilitator.py:234` was

```python
receiver = nb.destination if nb.subtype == "send" and nb.destination else pay_to
if receiver != pay_to:
    raise RpcError(...)
```

With `nb.destination` empty, `receiver` became `pay_to` and the next line compared `pay_to`
with itself — vacuously true. **The check that proves the seller's money arrived was skipped in
exactly the case where it could not be made**, and the `confirmed_sends` record then wrote
`"receiver": pay_to`, asserting a payee that had never been read.

**Measured, against the captured reply, before the fix:**

```
normalize_block_info -> destination = ''
seller's payTo : nano_1uw3f4f1...nkrmgiw4x
verification ok: True   reason=None

*** ACCEPTED. The seller is told they were paid. ***
   {'receiver': 'nano_1uw3f4f1...nkrmgiw4x', 'confirmed': True, ...}
   ...but the XNO went to nano_1natrium1o3z5519ifou7xii8crpxpk8y65qmkih8e8bpsjri651oza8imdd
```

The attack needs nothing privileged: a buyer owes the quoted amount, sends exactly that amount
**to its own second account**, and presents the confirmed block hash. Amount matches,
confirmation matches, the payee check does not run — the facilitator says paid, the seller does
the work, and nobody paid it. Both `verify` and `settle` go through this function, so the x402
`verify` and `settle` endpoints were both affected.

**The fix only narrows what is accepted.** `contents.link_as_account` is read first, and an
unreadable payee now **refuses** instead of being assumed:

```python
if not nb.destination:
    raise RpcError(f"block_info on {ep.url} carries no payee account, so it cannot "
                   f"prove who was paid; refusing rather than assuming payTo={pay_to}")
if nb.destination != pay_to:
    raise RpcError(f"block pays {nb.destination}, not payTo={pay_to} on {ep.url}")
```

`contents.link` is deliberately **not** a fallback: it is the payee as 64 hex characters rather
than as an account, so comparing it to a `nano_` payTo could only ever refuse a payment that was
in fact made. `confirmed_sends` now records the payee the block names, which is checked to equal
`pay_to`. Every previously accepted-and-correct payment still verifies; nothing that was refused
is now accepted.

**Why no test caught it.** Every existing stub puts the payee somewhere a real node does not —
top-level `link_as_account`/`destination`, or `contents: {"type": "send", "destination": ...}`.
`tests/test_facilitator_live.py` is named for the real node shape and uses
`contents: {"type": "send", "destination": REAL_PAYTO}`, which no node emits: a real state
block's `contents.type` is `"state"` and its payee key is `link_as_account`. So the suite only
ever exercised the branch where `destination` was populated, and the empty-destination branch —
the only one a real node reaches — was never run.

`tests/test_facilitator_real_node_shape.py` pins the captured reply verbatim: the payee is read
from `contents.link_as_account`, a send to a stranger is refused, a send to the right payee still
verifies, the recorded `receiver` is the payee the block names, a block with no payee field is
refused rather than assumed, a receive cannot pass as a payment, the amount is still compared
exactly, and an unconfirmed block is refused. **Reverting `nano_mcp/facilitator.py` alone turns
5 of the 9 red**, including the send-to-a-stranger one.

## Checked and clean

- **No float touches an amount** anywhere in `nano_mcp/` or `nano_sdk/`. `nano_sdk/units.py`
  converts by rebuilding the `Decimal` exponent rather than multiplying by `10**30`, because
  `Decimal` *arithmetic* rounds to the context precision (28 digits by default, fewer than the
  31 a whole-XNO raw balance carries) — the fix recorded in the 09-28 audit, still in place.
- `nano_to_raw`'s exception contract is one documented `ValueError` for every unusable input,
  including the `InvalidOperation` that `Decimal` raises and that an earlier version let escape.
  Re-probed: `"nan"`, `"inf"`, `True`, `"1e3"` and an over-precise amount all raise `ValueError`.
- **Fail-closed law L1 holds**: fewer than 2 independent endpoints refuses before any call, and
  any single endpoint erroring refuses the whole verification (`failures == 0` is the only `ok`).
- `normalize_block_info` treats a missing `confirmed` or `amount` as an error rather than as
  "not confirmed", and handles `confirmed` as the string `"true"` as well as the bool.
- No secret in the tree.

## Could not verify

- **No full x402 round trip against a live facilitator and a funded wallet.** The fix is proved
  against a node reply captured live, through a stub endpoint, not against a real payment
  settling. **The first live `verify`/`settle` after this lands is worth watching**: it is the
  first time the payee comparison will actually execute against a real node, because before this
  change it never did.
- **`NormalizedBlock.is_send` accepts `"state"` and `""` as well as `"send"`** and is left
  alone. It is permissive: `contents.type` on every state block is literally `"state"`, so a
  node that omits the top-level `subtype` would have a receive block pass this guard. With the
  payee check now actually running, such a block is refused on its payee instead — a receive
  block's `contents.link_as_account` is the source send's hash rendered as an account, not the
  seller's payTo — and `test_a_real_receive_block_cannot_pass_as_a_payment` pins both lines of
  defence. Tightening it to `subtype == "send"` would be a second refusal and is defensible, but
  it would also refuse a legitimate payment from a node that reports only `contents.type`, so it
  is reported rather than made.
- The `network`-marked tests (6 deselected, 6 skipped) were not run; they need a live node.

## Follow-up the same day: the payee fix was incomplete, and CI caught it

**I merged #18 without waiting for CI, on a green local run. CI was red.** The failing job was
`tests/test_facilitator_live.py::test_live_confirms_real_send_on_two_independent_public_rpcs`,
which calls two real public endpoints, and it failed on the new refusal:

```
live 2-RPC verification failed: block_info on https://rainstorm.city/api carries no
payee account, so it cannot prove who was paid; refusing rather than assuming
payTo=nano_1111111111111111111111111111111111111111111111111111hifc8npp
```

`rpc.nano.to` verified the same block fine. So the refusal was doing its job — but it had turned
a silent wrong answer into a refusal of a real payment, which for a seller is also a failure.

**Root cause: the `block_info` call omitted `json_block: "true"`.** Without it a node returns
`contents` as an opaque JSON **string**, and a state block's payee lives only in
`contents.link_as_account` — so there is nothing to read. `rpc.nano.to` is a wrapper that
normalises `contents` to an object either way, which is exactly why omitting the parameter looked
harmless and why the original defect survived a test named for the real node shape.
`rainstorm.city/api` is a plainer proxy and does not normalise.

This also explains why only the payee broke and not the amount or the confirmation: those are
**top-level** fields, unaffected by how `contents` is encoded.

Every sibling repository already asks for it — `nano-settlement-verify`'s
`{"action": "block_info", "json_block": "true", ...}`, and `nano_settlement_verify.py:130`
documents the string case in as many words: *"A node that ignores json_block returns contents as
an opaque string."*

**Two fixes, both narrowing nothing:**

1. The call now passes `json_block="true"`.
2. `_contents_of()` parses `contents` when it arrives as a string anyway, for a node that ignores
   the parameter. Unparseable contents read as absent and the payee refusal still fires.

Five more tests: the payee is read from string-encoded contents, a string-contents send to a
stranger is refused, a string-contents send to the right payee **verifies** (the case the live
test needs), non-JSON contents read as absent and refuse, and the request itself is asserted to
carry `json_block: "true"`.

**198 passed locally (193 before).**

## Could not verify (follow-up)

- **`rainstorm.city/api` is unreachable from this environment** — the egress policy denies the
  CONNECT with 403 — so the live test **skips** here and I could not confirm first-hand that this
  endpoint now yields a payee. What is confirmed is the shape question: a string-encoded
  `contents` now yields the payee, and the request asks for an object. If that endpoint returns a
  reply carrying no `contents` at all, the refusal will fire again and the live test will stay
  red; CI is the only window onto it from here, and its log is where the answer will be.
- **The lesson for this repository: do not merge here on a local run alone.** `nano-mcp` has a
  live, network-touching test inside the `not network` selection, so a local pass does not predict
  CI. Wait for the workflow.
