# nano-mcp — audit 2026-10-12 (b)

The `b` is this repository's convention for a second audit on one day: the day's first pass
is `audits/nano-mcp-2026-10-12.md`, on the branch of #30. That pass and the two merged this
morning (#28 payload guards, #29 the hex-case claim key) covered the facilitator's
`/verify`, `/settle` and claim store, and the SDK send path. **This pass deliberately took
the parts they did not**: the x402 *resource-server* half (`httpx402.py`), the MCP paid-tool
wrapper (`paidtool.py`), and the dollar-quote conversion (`pricing.py`).

## What I found and fixed

**The seller's half of the x402 handshake answered a malformed `payment-signature` by
dropping the connection.**

`ResourceApp.complete()` read the presented payload with `.get` as its first act
(`httpx402.py:190-191`):

```python
accepted = payload.get("accepted") or {}
request_id = str((accepted.get("extra") or {}).get("requestId") or "")
```

The payload is a stranger's bytes: a base64 `payment-signature` header, decoded by
`b64decode_json`, which returns whatever valid JSON the header carried — a list, a string, a
number. Each raised `AttributeError` out of `complete()`, and in the HTTP adapter that escaped
`do_GET` (`httpx402.py:288`), so `ThreadingHTTPServer` closed the socket with **no status line
at all** and printed a traceback per request. Measured against the real handler before the
fix, each of these five returned
`httpx.RemoteProtocolError: Server disconnected without sending a response`:

| `payment-signature` decodes to | raised at |
| --- | --- |
| `[1]` | `payload.get` — `'list' object has no attribute 'get'` |
| `"x"` | `payload.get` — `'str' …` |
| `5` | `payload.get` — `'int' …` |
| `{"accepted": [1], …}` | `accepted.get("extra")` |
| `{"accepted": {"extra": [1]}, …}` | `(accepted.get("extra") or {}).get` |

A buyer cannot tell its own bad payload from a seller that is down, so the sensible client
behaviour — retry a disconnect — is the wrong one here, and the seller serves nothing while
printing a stack trace for every attempt. This is the same defect class merged this morning
for the facilitator's `/verify` and `/settle` (#28); it was simply unfixed on the
resource-server half of the same handshake.

Fixed on `fix/resource-server-refuses-a-malformed-signature`: `complete()` refuses a payload,
an `accepted` or an `extra` that is not a JSON object, in the shape it already returns for a
payload it will not accept, so the HTTP adapter answers **402 with the reason**. One related
line goes with it: `_accepted_matches` read `accepted.get("extra", {})`, which returns `None`
for an `extra` that is present and null, and `.get` on it raised too.

- `tests/test_resource_server_refuses_a_malformed_signature.py`: 21 checks, **18 failing on
  `main`**, all 21 passing with the change, including the two controls (an unpaid request
  still gets its 402 challenge; a well-formed payload for an unknown request keeps its old
  requirements mismatch) and the assertion that no refusal ever produces the protected body.
- Nothing else in the suite moves: **466 passed** (445 + the 21 new checks), 16 skipped,
  same one live-network failure.

## What I found and did NOT fix

**An even-numbered median consults `decimal.getcontext().prec`, which this module never
sets.**

`fetch_median_xno_usd` requires at least 2 of its 3 sources, so during a single source outage
`median()` takes the even-numbered branch and computes `(a + b) / Decimal(2)` — Decimal
arithmetic, which rounds to the active *process-global* precision.
`usd_to_xno_raw` was rewritten (and its docstring argues the point at length) precisely so
that a quoted amount cannot move with "the `prec` of whatever program imported `nano_mcp`";
the rate that feeds it still can. Measured on this tree, two sources at 0.8234567 and
0.9123456 USD per XNO for a $0.01 call:

```
prec=28   median=0.86790115   raw=11522049486856884565713503203
prec=9    median=0.86790115   raw=11522049486856884565713503203
prec=6    median=0.86790      raw=11522064754003917502016361332
```

15,267,147,032,936,302,857,129 raw apart, and Nano has no memo — the amount *is* the tag a
payment is matched by.

It is reported rather than patched because the trigger needs **both** halves: a price-source
outage (the 3-source default takes the middle element and does no arithmetic at all) **and** a
caller that lowered `prec` below about 9, which is an unusual thing to do. The remedy is
small and local — compute that branch inside a `decimal.localcontext()` with a precision set
from the two operands, so it is exact and self-contained — and it is the owner's call whether
a defect this narrow is worth the lines.
