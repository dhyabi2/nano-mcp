## Found and fixed

**1. Legacy `xrb_` addresses could not be decoded, and the failure was an
`AssertionError`.** `crypto.ADDRESS_RE` admits both `nano_` and `xrb_`, but
`public_key_from_address` took the body with a fixed `address[5:]`. `xrb_` is
four characters, so the slice ate the first body character, the key field
decoded to more than 256 bits, and the `assert pub_n < (1 << 256)` guard fired.
`validate_address` only catches `ValueError`, so the assertion escaped a
function documented to return a bool. `Wallet.send()` validates its destination
and `build_send_block()` decodes its representative through this path, so no
`xrb_` value could be used at all. Fixed by splitting on the separator and
raising `ValueError` for an over-wide field. Test: the three node-verified
address vectors are now also decoded through their `xrb_` form.

**2. Balances needing more than 28 significant digits were rounded.**
`units.py` says "floating point is never used for money so no precision is ever
lost", but Decimal *arithmetic* rounds to the context precision, which defaults
to 28 — and a whole-XNO raw balance carries 31. `nano_str(9999999999999999999999999999999)`
returned `'10.00000000000000000000000000'`, i.e. it rounded *up*, reporting more
XNO than the account holds; `nano_to_raw(raw_to_nano(x))` did not round-trip;
and `nano_to_raw("1.000000000000000000000000000001")` was rejected as "more
precision than 10^-30 nano" about an amount with exactly that precision. Fixed
by rescaling the exponent (constructor and `int()` are exact and context-free)
instead of multiplying and dividing by `10**30`.

Both were proved by a test that fails on the unfixed tree and passes on the
fixed one. Suite after both changes: **30 passed, 5 deselected**.

## Found, not changed — for the owner to decide

**The daily cap is a UTC calendar-day bucket, not the rolling 24 hours the
docstring promises.** `Wallet` says "outbound total from any wallet is at most
0.01 XNO per day", and `_today()` keys spend on `int(time.time()) // 86400`. A
wallet that spends the full cap at 23:59 UTC may spend it again at 00:01 — 0.02
XNO inside two minutes. This is money code and is deliberately left alone here;
it needs the owner's call on which of the two behaviours is intended.

## Checked and clean

- No secrets in the tree. The only 64-hex literal is `DOCS_SEED` in
  `tests/test_crypto.py`, the published all-but-one-zero vector from
  docs.nano.org.
- `block.py` state-block layout, hashing and signing match the docs.nano.org
  receive vector byte-for-byte, and the test suite anchors it on that vector
  plus a live-chain hash recomputation rather than on narrative.
- `Account.__repr__` does not leak the private key; a test pins it.
- `client.py` raises on non-2xx and on an `error` key rather than returning a
  half-empty dict.
- README claims: `nano_mcp/` (the MCP server itself) does not exist yet, but the
  README says "later blocks" in both places it is mentioned, so it does not
  promise something absent. The `Status` line still says "Block 2" while the
  tree is at block 3 — stale, not wrong.
- `test_units_roundtrip` only exercises values of one significant digit, which
  is why defect 2 passed through it. Widened by this audit.
