## Found and fixed

**`.gitignore` did not cover `build/` or `dist/`, so the repository's own
documented setup left a second complete copy of the SDK where `git add -A` would
commit it.** `.gitignore` listed `__pycache__/`, `*.pyc`, `.venv/`,
`.pytest_cache/` and `*.egg-info/` and stopped there. After
`uv pip install -e ".[dev]"` and `python -m build` — the two commands the README
gives — the tree holds `build/lib/nano_sdk/` and `dist/`, and:

```
$ git add -A --dry-run
add 'build/lib/nano_sdk/__init__.py'
add 'build/lib/nano_sdk/block.py'
add 'build/lib/nano_sdk/client.py'
add 'build/lib/nano_sdk/crypto.py'
add 'build/lib/nano_sdk/units.py'
add 'build/lib/nano_sdk/wallet.py'
add 'dist/nano_mcp-0.1.0-py3-none-any.whl'
```

`wallet.py` is the daily cap and the send path. A committed copy of it would then
age in place while `nano_sdk/` moved on.

**This is not a hypothetical.** The sibling repository
`dhyabi2/openai-agents-nano-x402` had the same gap and did commit its
`build/lib/`; audited earlier in this same run, the tracked copy had gone 418
bytes stale and what it was missing was the `is_finite()` guard that refuses a
model-supplied `max_xno` of `"nan"` or `"Infinity"`. So that repository's public
tree carried a second, weaker copy of a guard on model-controlled input. Here the
duplicate would be money code, which is worse.

Fixed by adding `build/` and `dist/` to `.gitignore`. Nothing was removed: no
build artifact is tracked in this repository yet, so this is the gap closed
before it cost anything. The five existing entries are unchanged.

Proved rather than asserted. `tests/test_repo_tree.py` asks git what it ignores
and what it tracks, rather than reading the `.gitignore` text, since the
behaviour is the property that matters. Against the unfixed `.gitignore`:

## Still open for the owner — unchanged from 2026-09-24 and 2026-09-25

**The daily cap is a UTC calendar-day bucket, not the rolling 24 hours the
docstring promises.** `Wallet`'s docstring says "outbound total from any wallet is
at most 0.01 XNO per day" and the comment at `wallet.py:52` and `:59` says
"rolling", while `_today()` keys spend on `int(time.time()) // 86400`. A wallet
that spends the full cap at 23:59 UTC may spend it again at 00:01 — 0.02 XNO
inside two minutes. Money code, deliberately untouched; it needs the owner's call
on which of the two behaviours is intended.

## Noted, not changed — money code, for the owner

- **A send whose response is lost is not counted against the cap.**
  `wallet.py:164` records the spend only after `process` returns, which the
  comment states deliberately ("Only record the spend once the block is accepted
  by the node"). But if the node accepts the block and the HTTP response is then
  lost — a timeout, a reset — `httpx` raises, `_record_send` never runs, and the
  money has moved uncounted. The next send sees the full cap available. The
  opposite choice loses the other way (recording a send the node refused), so
  which failure is preferable is the owner's call, not an audit's.
- **`result["hash"]` at `wallet.py:162` is unguarded.** A `process` response
  without a `hash` key raises `KeyError` rather than a named error, after the
  block has been published. Same reason for leaving it: it is on the send path.

## Checked and clean

- **No secrets in the tree.** A sweep of every tracked file for private-key
  headers, `ghp_`/`github_pat_`/`xoxb-`/`AKIA`/`sk-` shapes found nothing. The
  only 64-hex literals are in `tests/test_block.py`, `tests/test_crypto.py` and
  `.ledger/ledger.json`: the published all-but-one-zero vectors from
  docs.nano.org plus block hashes, which are public by definition. No `.env`,
  `.pem` or `.key` file is tracked.
- The `network` marker is registered in `pyproject.toml`, so the README's
  `pytest -m "not network"` deselects rather than warning, and the live tests
  additionally `skipif` on `NANO_RPC_URL` — which is why a plain `pytest` skips
  them instead of failing. Both commands the README gives work as written.
- `tests/test_packaging.py` still passes with a fourth file in `audits/`: the
  explicit `[tool.setuptools.packages.find]` added on 2026-09-25 means adding
  audit notes cannot break the build again, and the wheel carries `nano_sdk` and
  nothing else.
- `client.py` raises on non-2xx and on an `error` key rather than returning a
  half-empty dict, and the API key is sent as a header, never in a URL or a log
  line.
- `RpcBalanceError` is defined below the class that raises it, which looks wrong
  and is not: the name is resolved when the method runs, and the module has
  finished importing by then. `nano_sdk/__init__.py` exports it, and a live
  import confirms it.
