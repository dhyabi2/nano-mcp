## Found and fixed

**1. `nano_to_raw` documents ValueError and raised two different exceptions.** Its docstring tells a
caller to handle `ValueError`; it builds the amount with `Decimal(str(amount))`, and Decimal signals
a malformed literal with `InvalidOperation`, which inherits from `ArithmeticError`. So:

```
'abc'   -> InvalidOperation   escapes `except ValueError`
''      -> InvalidOperation   escapes
'1,5'   -> InvalidOperation   escapes
None    -> InvalidOperation   escapes
'nan'   -> ValueError         caught
```

The same function answered two types for two kinds of input that are both simply not an amount —
`nan` only because it reached the `is_finite()` check one line further down. This is the conversion
an agent points at an amount it was handed, in a package whose claim is paying per call. Re-raised
as `ValueError` with the value in the message and the original chained. No conversion result moves,
and nothing valid becomes invalid — pinned by a second law over `str`, `int`, `Decimal`, scientific
notation both ways, zero and negative zero.

**2. `RpcClient.call` let two kinds of bad answer past `RpcError`.** `RpcError`'s docstring said it
covers "an error payload or a non-2xx response". A **200 whose body is not JSON** raised
`json.JSONDecodeError`, and a **200 whose body is JSON but not an object** was returned as-is from a
method annotated `-> dict`:

```
200 with an HTML proxy page  -> JSONDecodeError   escapes `except RpcError`
200 with an empty body       -> JSONDecodeError   escapes
200 with a JSON list         -> returned [1, 2]
```

The first is the realistic one: a 200 carrying HTML is not the node talking, it is whatever sat in
front of it — a proxy error page, a captive portal, a CDN interstitial. This swarm has already been
bitten by that exact shape (Cloudflare answering a default User-Agent with `error code: 1010`). The
second pushes the failure into the caller, which does `data["balance"]` on a list and raises
`TypeError` a long way from the cause. Both are `RpcError` now, with the body quoted so the cause is
readable, and the docstring states the full contract. The two cases that already raised still raise,
and an ordinary object answer — including `{}` — still returns, both pinned.

## Found, not fixed

- **The daily cap is a UTC calendar-day bucket, not the rolling 24 hours the docstring promises.**
  `Wallet` says "outbound total from any wallet is at most 0.01 XNO per day" and the comment at
  `wallet.py:59` says "rolling 24h", while `_today()` keys spend on `int(time.time()) // 86400` — so
  a wallet that spends the full cap at 23:59 UTC may spend it again at 00:01. Carried forward from
  the 2026-09-25 note, still money code, still the owner's call on which of the two behaviours is
  meant. Untouched.
- **`send()` records the spend only after `result["hash"]` succeeds** (`wallet.py:162`). If the node
  accepts the block and answers 200 without a `hash` key, the block is on chain and
  `_record_send` never runs, so the cap under-counts a send that really happened. Money code;
  reported rather than changed.
- **`send()` validates the node's PoW reply with a bare `assert`** (`wallet.py:143`), which `python -O`
  removes. Under `-O` a missing `work` becomes a `KeyError` one line later and a non-string `work`
  reaches the block dict. Money path; left for the owner with the two above, so all three move
  together.
- **`mcp>=1.0` is a hard runtime dependency that nothing in the package imports.** `grep` for
  `import mcp` across the tree finds nothing, and the wheel installs **37 packages** into an empty
  venv — pydantic, cryptography, uvicorn, starlette, PyJWT, opentelemetry — for an SDK the README
  calls "pure-Python" and which needs only `httpx` and `ed25519-blake2b-fork`. The README says the
  MCP server arrives in "later blocks", so whether the dependency is declared early on purpose is a
  roadmap decision, not an auditor's: reported, not changed. Moving it to
  `[project.optional-dependencies]` would be one line when wanted.
- **The README's "Repo layout" lists `nano_mcp/`**, which does not exist in the tree and is not
  importable from the installed wheel (`ModuleNotFoundError: No module named 'nano_mcp'`) — while the
  distribution is *named* `nano_mcp` and the description opens "An MCP server + SDK". It is marked
  "(later blocks)", so this is the same roadmap question as the dependency above and is recorded with
  it rather than edited away.

## Read and found sound

- **`crypto.py`.** Derivation is `blake2b(seed || uint32be(i))` as the spec says; the address is
  52 fixed-width base32 of the big-endian key plus 8 of the byte-reversed `blake2b-40` checksum;
  `public_key_from_address` splits on `_` rather than a fixed offset, so a legacy `xrb_` address is
  not truncated, and it **fails closed** on a checksum mismatch. `Account.__repr__` cannot leak the
  private key.
- **`block.py`.** The hashed byte string is preamble(32) ‖ account ‖ previous ‖ representative ‖
  balance(16, big-endian) ‖ link, each length-checked, with the balance range-checked to 128 bits —
  transcribed correctly, and pinned to the docs.nano.org send/receive/first-receive vectors.
- **`units.py`'s reason to exist holds.** Conversions rescale the exponent rather than multiplying by
  `10**30`, so a whole-XNO raw balance (31 significant digits) is exact where Decimal's default
  28-digit context would have rounded it; `nano_str` trims digits rather than calling `normalize()`,
  for the same reason.
- **`check_send`** refuses a non-positive amount, an overdraw and a cap breach before anything is
  signed, and `send()` treats a missing balance as `0`, which fails in the safe direction.

## Not verified

- **The 5 network-marked tests.** They need a live node and a key this sandbox does not have, so the
  RPC client against the real `rpc.nano.to` — response shapes, the `x-api-key` header, whether
  `process` really answers `{"hash": …}` — is unverified by this run. The new offline laws exercise
  `call`'s handling of answers, not the node's actual replies.
- **No block was built against a live frontier and no send was broadcast.** `wallet.send` is
  exercised only through the stub client in `tests/test_wallet.py`.
- **Whether `audits/` should ship inside the sdist.** It is excluded from the wheel, which is what a
  user wants; if the notes should travel with the sdist that is a separate decision.
