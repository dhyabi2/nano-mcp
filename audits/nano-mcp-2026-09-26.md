# nano-mcp — code audit, 2026-09-26

Scope: the tree at `85ce432` (`main`). Baseline in a clean virtualenv, before any change:

```
$ pip install -e ".[dev]"                  # succeeds (the 09-25 packaging fix holds)
$ python -m pytest -m "not network" -q
36 passed, 5 deselected
$ python -m build --wheel
Successfully built nano_mcp-0.1.0-py3-none-any.whl
  top-level contents: ['nano_mcp-0.1.0.dist-info', 'nano_sdk']
```

The 09-24 audit read `nano_sdk/` line by line. Repeating that would have found nothing, so this run
instead **drove the pure functions against their own stated contracts** — 20,000 random raw values
through the unit conversions, 500 random public keys through the address codec in both prefixes, and
every malformed shape of an address a caller can plausibly hold. The one defect below came out of the
last of those. The 5 `network`-marked tests were not run: they need a live node and a key this sandbox
does not have.

## Found

**An address with a trailing newline crashed the decoder with `KeyError` instead of being refused.**
`crypto.py:24` anchors `ADDRESS_RE` with `$`, and in Python `$` also matches *immediately before a
trailing newline*. So `"nano_<60 chars>\n"` passed the regex, `body` came out 61 characters long, and
`_b32_decode` reached the `"\n"`, which is not in the Nano alphabet:

```
ADDRESS_RE matches a valid address + "\n" : True
validate_address(addr)                    -> True
validate_address(addr + "\n")             -> RAISED KeyError('\n')
public_key_from_address(addr + "\n")      -> RAISED KeyError('\n')
addr read back with readline(), validated -> RAISED KeyError('\n')
```

Two documented contracts are broken by it. `public_key_from_address` says it "Raises ValueError if the
address is malformed"; `validate_address` says it returns a bool and catches only `ValueError`, so the
`KeyError` escapes it. This is the *same contract violation* the 09-24 audit fixed on this very
function when an `AssertionError` was escaping — a second route to it was still open.

It is not exotic. A trailing newline is the ordinary shape of an address read from a file, a config or
a piped command, and `Wallet.send` validates its destination through this path (`wallet.py:126`), so a
caller passing a newline-terminated destination gets `KeyError('\n')` rather than the wallet's own
"invalid destination". It also cannot be caught by the obvious `except ValueError`.

**Fixed** by anchoring with `\Z`, which matches only the true end of the string, so a trailing newline
is malformed — which it is. Nothing else changed.

Proved both directions. Against the unfixed `crypto.py`:

```
FAILED tests/test_crypto.py::test_an_address_with_a_trailing_newline_is_malformed_not_a_crash
E           KeyError: '\n'
nano_sdk/crypto.py:35: KeyError
```

With the fix, in the same venv: **38 passed, 5 deselected** (36 before). The second new test exists to
pin the other direction — that refusing the malformed tail changes no valid address: 25 derived
accounts still decode to the key they were built from, in both `nano_` and `xrb_` form.

**Not merged by this audit.** `crypto.py` is the address/key path, which the standing instruction for
these runs excludes from self-merging, so the change is a pull request left open for a person. Two
notes for whoever reviews it: the change can only *refuse* more (it accepts nothing it did not accept
before, pinned by the second test), and the same `$` anchor is live in the sibling
`dhyabi2/nano-mcp-public`, where the same fix is raised separately and also left open. Worth recording
that the 09-24 run *did* merge a `crypto.py` fix in this repository while the 09-25 run left the
identical fix open in the sibling; the two runs applied different rules to the same file, and the
cautious one is the one followed here.

## Found, not fixed — for a person

**This repository has no licence at all, and its public sibling is MIT.** There is no `LICENSE` file
and no `license` field in `pyproject.toml`, while `dhyabi2/nano-mcp-public` carries both a `LICENSE`
and `license = {text = "MIT"}`. A public repository with no licence is "all rights reserved" by
default: anyone who reads the README and installs it has no granted right to use, copy or modify it,
which is the opposite of what publishing it was for. Stating a licence is the owner's declaration to
make, not an auditor's, so nothing was added — but it is the cheapest fix on this list and the one
most likely to matter to a stranger.

**Two repositories publish `nano-mcp` version `0.1.0` with different code.** Both `pyproject.toml`
files declare `name = "nano-mcp"` and `version = "0.1.0"`; the trees are not the same. This one is the
smaller: it has no `nano_mcp/` server package, and `nano_sdk` here lacks `build_receive_block` and
`Wallet.receive`, which the sibling has. So `pip install "nano-mcp @ git+…"` gives two materially
different packages under one name and one version depending on which URL was used, and the PyPI name
(still unregistered) can only ever be one of them. Which repository is the distribution is a release
decision for a person.

**A drift in the money path, reported and not touched.** `wallet.py:134` here reads
`info.get("representative", self.representative)`; the sibling reads
`info.get("representative") or self.representative`. The two differ when a node returns the key with
an empty or null value: this version passes `""` on to `public_key_from_address` and raises, where the
sibling falls back to the configured representative. `wallet.py` is money code and is deliberately
left alone; it is recorded so the divergence is a decision rather than an accident.

**Unchanged from 09-24 and 09-25: the daily cap is a UTC calendar-day bucket, not the rolling 24 hours
the docstring promises.** `Wallet` says "outbound total from any wallet is at most 0.01 XNO per day"
while `_today()` keys spend on `int(time.time()) // 86400`, so a wallet that spends the full cap at
23:59 UTC may spend it again at 00:01. Money code; it needs the owner's call on which behaviour is
intended. Three audits have now reported it.

## Checked and clean

- **Unit conversions.** 20,000 random raw values in `[0, 10**33)`: `nano_to_raw(raw_to_nano(x)) == x`
  and `nano_to_raw(nano_str(x)) == x` for every one. The 09-25 exponent-rescaling fix holds, including
  where Decimal's 28-digit context precision used to round. Odd inputs behave: `NaN` and `Infinity`
  raise `ValueError`, `"1e-30"` is exactly 1 raw, `".5"`, `"+1"` and `" 1 "` parse.
- **The address codec.** 500 random public keys encode and decode back byte-for-byte, in both
  `nano_` and `xrb_` form, and `validate_address` agrees with the checksum on all of them.
- **No secrets in the tree.** 14 lines are 64-hex shaped: 6 in `tests/test_block.py`, 6 in
  `tests/test_crypto.py` — the published `docs.nano.org` all-but-one-zero seed vectors and the keys
  derived from it, which the 09-25 sibling audit verified resolve to the documented example account
  and to no account this swarm holds — and 2 block hashes in `.ledger/ledger.json`, which are public
  by definition. No `.env`, `.pem` or `.key` is tracked, no token shapes, no private-key blocks, and
  nothing of that kind appears in the history available to a shallow clone.
- **Packaging.** `pip install -e ".[dev]"` and `python -m build --wheel` both succeed, and the wheel
  carries `nano_sdk` and nothing else — the audit notes and the tests are not shipped. The 09-25
  `[tool.setuptools.packages.find]` fix is doing its job, and `audits/` gaining a third file did not
  break it.
- **The README** makes no external claims to check: it contains no links, and (unlike the sibling) no
  install command pinned to a tag.
- `nano-mcp` is still not on PyPI (`pypi.org/pypi/nano-mcp/json` → 404), so no published artefact
  carries any of this.

## Not verified

- The 5 `network`-marked tests (`test_client.py` in full, one live block-hash recomputation). They
  reach the live `rpc.nano.to` node and need `NANO_RPC_KEY`, which this sandbox has neither of. None
  of them imports the changed line, so nothing in this change can affect them — but they were not
  run, which is the reason the fix is left open rather than merged.
- The live send path end to end. It needs a funded wallet, and an audit should not be moving money.
