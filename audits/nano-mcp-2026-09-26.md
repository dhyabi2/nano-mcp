# nano-mcp — code audit, 2026-09-26

Scope: the published tree at `85ce432` (`main`). The SDK was read in full by the
2026-09-24 audit and `nano_sdk/` has not changed since, so this run went looking
for the class of defect the previous two missed rather than re-reading for the
same ones: what the library *prints*, and what the test stubs assume about the
node.

## How it was checked

```
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"
.venv/bin/python -m pytest -m "not network" -q    # 36 passed, 5 deselected  <- baseline
.venv/bin/python -m build --wheel                 # nano_mcp-0.1.0-py3-none-any.whl
```

Baseline green before any change, so the fix below is the difference. The
network-marked tests were not run: this sandbox's egress policy refuses
`rpc.nano.to:443` outright (`connect_rejected`), so nothing in this run touched
a live node.

## Found and fixed

**`repr(Wallet)` printed the wallet seed in full.** `crypto.Account` overrides
`__repr__` specifically so a private key cannot reach a log, and
`test_account_repr_hides_private_key` pins that. `Wallet` holds the *seed* — from
which every account's private key derives, so strictly worse than one key — and
was left a plain `@dataclass`, whose generated `__repr__` prints every field.
`seed` is the first field:

```
>>> repr(Wallet(seed="9f0e444c…120f"))
"Wallet(seed='9f0e444c69f77a49bd0be89db92c38fe713e0963165cca12faf5712d7657120f', client=…"
```

This is not only a `print(wallet)` away. Anything that reprs local variables
carries it, so a *failure* is what publishes the seed. One overdrawn-send test
failing under `pytest -l` printed it four times — once as the test's local, three
times as `self` down the `send` frames:

```
$ pytest leak_demo.py -l -q | grep -c 9f0e444c
4
```

The same is true of `logging.exception`, a debugger, and any traceback-with-locals
an agent captures into its own run log — which on these boxes is journalled and
published. No value is exposed by the repository itself; the leak is in what the
published library does with its caller's seed.

Fixed with `seed: bytes | str = field(repr=False)`, mirroring the guard `Account`
already has. The field stays mandatory and the seed stays readable and usable —
only its printing changed.

Proved rather than asserted. `test_wallet_repr_does_not_leak_the_seed` checks
`repr`, `str`, an f-string and `%r`, for both a hex-string and a `bytes` seed.
Against the unfixed tree:

```
FAILED tests/test_wallet.py::test_wallet_repr_does_not_leak_the_seed
  assert '9f0e0e0e…' not in 'Wallet(seed=…'
1 failed, 6 passed
```

With the fix: **37 passed, 5 deselected**, the leak demo grep drops to 0, and the
wheel still builds carrying `nano_sdk` and nothing else.

## Found, not verified — needs the owner or a box with node access

**`Wallet.send` may be silently rewriting the account's representative on every
send, and the test stub would not notice.** `send` does:

```python
rep = info.get("representative", self.representative)
```

`self.representative` defaults to `DEFAULT_REPRESENTATIVE` (NanoFusion). Per
docs.nano.org, `account_info` does **not** return a `representative` field unless
the request passes `representative="true"` — it returns `representative_block`.
If that is right, then the `.get` always falls through to the default and every
send writes NanoFusion into the block as the account's representative, silently
moving a user's chosen representative. `tests/test_wallet.py`'s `StubClient`
returns a hand-written `account_info` that *does* include `representative`, so
the suite cannot see it either way.

Not fixed here, for two reasons: this run cannot reach `rpc.nano.to` to
demonstrate the real response shape, and the fix would be in the send path, which
is money code. It needs one live `account_info` read from a box that has node
access. If confirmed, the fix is to pass `representative="true"` through
`client.account_info` and to make the stub mirror the real shape.

## Still open for the owner — unchanged from 2026-09-24 and 2026-09-25

**The daily cap is a UTC calendar-day bucket, not the rolling 24 hours the
docstring promises.** `Wallet` says "outbound total from any wallet is at most
0.01 XNO per day" while `_today()` keys spend on `int(time.time()) // 86400`, so
a wallet that spends the full cap at 23:59 UTC may spend it again at 00:01. Money
code, deliberately untouched; it needs the owner's call on which behaviour is
intended.

## Checked and clean

- No secrets in the tree. The 64-hex literals are the published docs.nano.org
  test vectors (`DOCS_SEED`, `DOCS_PUB`, `DOCS_PRIV`) plus block hashes, which are
  public by definition. No `.env`, `.pem` or `.key` is tracked.
- `pyproject.toml` still installs and builds: the explicit
  `[tool.setuptools.packages.find]` added on 09-25 survives this run's new files,
  and `tests/test_packaging.py` pins it.
- README claims were re-checked against the tree. `nano_mcp/` still does not
  exist, and both mentions still say "later blocks", so nothing absent is
  promised. The `Status` line still reads "Block 2" while the tree is at block 3 —
  stale, not wrong, and not worth a commit on its own.
- README carries no external hyperlinks, so there is no dead link for a reader to
  hit.
- `Account` is `frozen=True` with the guarded `__repr__`; no other dataclass in
  `nano_sdk/` holds a secret field.

## Observed, not changed

`.gitignore` covers `__pycache__/`, `*.pyc`, `.venv/`, `.pytest_cache/` and
`*.egg-info/`, but not `build/` or `dist/` — the output of the `python -m build`
the README and these audits both run. A contributor following the README can
commit a wheel without noticing; this audit nearly did. Left alone because it is
not this branch's concern and does not affect anyone installing the package.

## Not verified here
