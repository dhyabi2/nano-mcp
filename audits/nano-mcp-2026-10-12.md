# nano-mcp — audit 2026-10-12

Through the lens: *can an agent pay, or get paid, in XNO with this today without being hurt?*

Base: `3296481` (`A requirement for amount "-0.5" verified against a 0.5 XNO send (#27)`).
Installed from the declared dependencies (`pip install -e ".[dev]"`). Suite green before
any change: **293 passed, 11 skipped, 1 failed** — the one failure is
`tests/test_pricing.py::test_live_median_of_three_sources_returns_numeric`, which reaches
three live price APIs and gets `httpx.ProxyError: 403 Forbidden` from this environment's
network policy. It fails identically before and after this change and is not a defect in
the repository. With this branch: **325 passed, 12 skipped, 1 failed** (the same one).

Four audits in four days have gone at the facilitator (#24, #25, #26, #27). This run went
at the other side — the SDK that signs and publishes the send — and at the one thing the
offline suite cannot see: what the node actually answers.

## Checked

- **No float touches an amount.** `nano_sdk/units.py` converts by rescaling the `Decimal`
  exponent (`as_tuple()` rebuilt with a moved exponent), never by multiplying by `10**30`,
  so the 28-digit default context cannot round a whole-XNO balance; `nano_to_raw` refuses
  a non-number, a non-finite, a negative and anything finer than 10⁻³⁰ with `ValueError`
  and nothing else. `nano_mcp/pricing.py:131` builds the dollar quote from
  `as_integer_ratio()` in pure integers. The only `10**30` multiplications in the tree are
  integer ones.
- **`check_send` runs before anything is signed**, rejects a `bool` explicitly (it is an
  `int` subclass, and `balance - True` once published a real 1-raw send), rejects a
  non-`int`, a non-positive amount, an overdraw and the daily cap. `Wallet.send` reads
  balance and frontier from one `account_info`, so the guard and the block agree.
- **The block bytes.** `nano_sdk/block.py` pins all six state-block fields to 32/32/32/16/32
  bytes and refuses a balance outside 128 bits before hashing; the hash is blake2b-256 and
  the signature Ed25519-Blake2b over that digest, with the docs.nano.org vectors as tests.
- **`RpcError` is still the one exception a caller must handle** (`nano_sdk/client.py:30`):
  a non-200, a body that is not JSON, a body that is not an object, and an object carrying
  `error` all raise it. `tests/test_client_offline.py` holds each.
- **The facilitator's amount discipline**, unchanged by this branch and now very tight:
  `is_amount_string` is a `fullmatch` on `[0-9]+(\.[0-9]{1,30})?`, so the `int()`-isms that
  made `"-0.5"` read as `+0.5` XNO (#27) are refused before `parse_raw` sees them, and
  `_check_requirements` enforces `REQUIRED_SECTIONS` rather than comparing a request
  against itself (#24).
- **Secrets:** no seed, key or token value in the tree. `Wallet` is a dataclass with
  `seed: … = field(repr=False)` and `Account.__repr__` hides the private key, so neither
  reaches a traceback with locals.

## Found and fixed — every send silently re-delegated the account it paid from

Both send paths carry the account's existing representative into the block they sign:

```
nano_sdk/wallet.py:153   rep = info.get("representative", self.representative)
nano_sdk/buyer.py:298    rep = info.get("representative", self.account.address)
```

A fallback is right for an unopened account, which has no representative yet. But
`nano_sdk/client.py:63` called `account_info` **without** `representative="true"`, and a
Nano node does not send that key unless asked. Read from the live node this run:

```
$ account_info                        -> account_version, balance, balance_nano,
                                         block_count, confirmation_height,
                                         confirmation_height_frontier, frontier,
                                         modified_timestamp, open_block,
                                         representative_block
$ account_info representative=true    -> ... + representative
```

So the read **never** found a representative and the fallback was taken on every send: a
`Wallet` re-pointed the paying account at `DEFAULT_REPRESENTATIVE` (NanoFusion), and a
`SessionWallet` re-pointed the session sub-account at **itself** — an account with no
voting weight behind it. The representative is a hash-covered field of the state block, so
this is a real, signed change to the ledger every single time money moves, and it
contradicts `wallet.py`'s own module docstring ("account_info for
balance/frontier/representative") and `send`'s ("balance + frontier + representative
atomically").

Nothing noticed because **every stub in the suite answers `account_info` with a
`representative` key the real node never sends** (`tests/test_wallet.py:31`,
`tests/test_buyer.py:59`, `tests/test_probe.py:66`). The offline suite therefore modelled a
node response that does not exist. Both stubs now carry a note saying what they stand in
for; `tests/test_send_keeps_the_representative.py` replaces `httpx.post` with a
`FaithfulNode` that answers the way rpc.nano.to actually does — the field appears only when
the request asks for it — so a send is exercised end to end through the real `RpcClient`.

Fixed in four code commits on this branch; the rule they end at is stated after them.

**`85fb399` (this routine):** ask the node for the field, and read it with `or` rather
than a default argument so a blank answer falls back instead of handing `""` to
`public_key_from_address`.

**`8e4827f` (a second routine, reviewed here):** that first commit made the node's
representative win over `Wallet(representative=X)` — a caller who had deliberately chosen
one was silently overridden, which is a regression the first commit introduced and this one
removes. At that commit `Wallet.representative` defaulted to `None`, `__post_init__` recorded
whether one was passed (and left the attribute reading as an address; replaced in `3c2bea0`,
below), and `_send_representative` prefers a caller's choice over the node's. It
also routes both send paths through a new `client.representative_from_info`, which
validates the node's answer — `RpcError` for a non-string or a value that is not a
checksum-valid `nano_` address — **before** a `work_generate` round-trip is spent, and
treats a missing, null or blank answer as "none" so the fallback is taken. Verified here:
no import cycle (`crypto.py` imports nothing from the package), `validate_address` really
is checksum-validating, and the suite is green.

**`f4fc8b6` and `3c2bea0` (superseded design, then the current one):** `8e4827f` kept the
attribute reading as an address by recording "was one passed?" in a hidden dataclass field
and overwriting `None` with `DEFAULT_REPRESENTATIVE` in `__post_init__`. That made the
field behave unlike a plain field: `dataclasses.replace` of a wallet built without one
produced a copy that signed `DEFAULT_REPRESENTATIVE` (re-delegating), `Wallet(**asdict(w))`
raised `TypeError`, equality depended on the hidden flag, assigning `None` later raised,
and assigning exactly `DEFAULT_REPRESENTATIVE` later was indistinguishable from never
setting one (`f4fc8b6` documented that last case). `3c2bea0` removes the hidden field and
the overwrite. `Wallet.representative` is now kept exactly as given.

The rule now, in `Wallet._send_representative`:

- **`None`** (the default, or assigned later): keep the account's current representative,
  the one the node reports. Only an account with none (unopened, or a null or blank answer)
  gets `DEFAULT_REPRESENTATIVE`.
- **Any address**, passed to the constructor or assigned later, `DEFAULT_REPRESENTATIVE`
  included, is an explicit choice. It is validated (`ValueError` before `work_generate` if
  it is not a valid `nano_` address) and every send signs it.
- **The node's representative is validated before work** by `client.representative_from_info`:
  a non-string or a value that is not a checksum-valid `nano_` address raises `RpcError`,
  and nothing is requested after `account_info`, signed or broadcast. It is only consulted
  when the wallet's own value is `None`. `SessionWallet` has no representative option. It
  uses the same validated node value, falling back to the sub-account's own address.

| how the representative was set | block signs |
| --- | --- |
| nothing passed, node reports one | the node's |
| nothing passed, node reports none or blank | `DEFAULT_REPRESENTATIVE` |
| `Wallet(representative=THIRD)` | THIRD |
| `Wallet(representative=DEFAULT_REPRESENTATIVE)` | the default |
| `w.representative = THIRD` after construction | THIRD |
| `w.representative = DEFAULT_REPRESENTATIVE` after construction | the default |
| `w.representative = None` after construction | the node's |

## Found, not fixed

- **`pay_and_fetch` pays `accepts[0]` without reading its scheme, network or asset**
  (`nano_mcp/httpx402.py:338`). Against this repository's own resource server that is
  always the one Nano offer, and the docstring scopes the function to "the demo and tests";
  against a multi-rail seller the first offer can be USDC on another network, and a Nano
  payer would then fail at `validate_address` rather than skip the offer. `langchain-vend`
  solves the same problem with a `_payable()` filter. A fix is small but it changes which
  offer is paid, so it is the owner's call rather than a refusal.
- **`result["hash"]` after `process`** (`wallet.py:181`, `buyer.py:325`) raises `KeyError`
  on a 200 that carries neither `error` nor `hash`. `RpcClient.call` already raises
  `RpcError` for an `error` key, so this is a narrow shape, and the spend is correctly not
  recorded — but the caller gets a `KeyError` where the module documents `RpcError`.
- **The daily cap is per UTC day, not rolling 24 h**, while `wallet.py:63` says
  "(rolling 24h)". `_today()` resets `_spend` when `time()//86400` changes, so 0.01 XNO at
  23:59 and 0.01 XNO at 00:01 both pass. AGENTS.md says "at most 0.01 XNO per day", which a
  UTC day satisfies; the comment is the thing that drifted. Also: `_record_send` runs only
  after `process` returns, so two concurrent `send()` calls on one `Wallet` can both pass
  `check_send` and exceed the cap together.
