# nano-mcp — code audit, 2026-09-25

Scope: the tree at `8855353` (`main`). This run began by re-running yesterday's
own checks rather than reading new code, which is what caught the one defect
below: the repository had stopped installing since the last audit, and nothing
in the test suite could tell.

## How it was checked

```
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"      # FAILED on the tree as published
.venv/bin/python -m build --wheel      # FAILED, same cause
PYTHONPATH=. .venv/bin/python -m pytest -m "not network" -q
                                       # 34 passed, 5 deselected  <- baseline
```

The suite had to be run over `PYTHONPATH` because the package could not be
installed at all. The network-marked tests were not run: this sandbox has no
`NANO_RPC_KEY` and they hit the live `rpc.nano.to` node.

## Found and fixed

**The distribution no longer built, so `pip install` could not work.** With no
packaging configuration in `pyproject.toml`, setuptools falls back to
flat-layout auto-discovery, which refuses to build as soon as the repository
root holds more than one directory that could be a package — rather than guess
which one is the distribution. `audits/`, added by the previous audit, was the
second one:

```
$ pip install -e ".[dev]"
  error: Multiple top-level packages discovered in a flat-layout:
         ['audits', 'nano_sdk'].
× Getting requirements to build editable did not run successfully.
```

`python -m build --wheel` fails identically. The SDK itself was never at fault
and every test went on passing, because the suite imports `nano_sdk` from the
working tree — only someone installing the package saw it.

Fixed by stating the packages instead of relying on discovery, the same way the
sibling repository `nano-mcp-public` already does:

```toml
[tool.setuptools.packages.find]
include = ["nano_sdk*"]
exclude = ["tests*", "audits*"]
```

Proved rather than asserted. `tests/test_packaging.py` runs the backend hook the
installer runs first, from the repository root, and checks that what it selects
is `nano_sdk` and not `audits` or `tests`. Against the unfixed `pyproject.toml`:

```
FAILED tests/test_packaging.py::test_build_backend_resolves_the_package_list
FAILED tests/test_packaging.py::test_the_sdk_is_the_package_that_ships
2 failed
```

With the fix, in a clean virtualenv:

```
$ pip install -e ".[dev]"                 # succeeds
$ python -m build --wheel
Successfully built nano_mcp-0.1.0-py3-none-any.whl
  top-level contents: ['nano_mcp-0.1.0.dist-info', 'nano_sdk']
$ python -m pytest -m "not network" -q
36 passed, 5 deselected
```

The wheel carries `nano_sdk` and nothing else — the audit notes and the tests
are not shipped to users.

No published artifact was affected: `nano-mcp` is still not on PyPI
(`pypi.org/pypi/nano-mcp/json` → 404), so the damage was limited to anyone
installing from the repository.

## Still open for the owner — unchanged from 2026-09-24

**The daily cap is a UTC calendar-day bucket, not the rolling 24 hours the
docstring promises.** `Wallet` says "outbound total from any wallet is at most
0.01 XNO per day" while `_today()` keys spend on `int(time.time()) // 86400`, so
a wallet that spends the full cap at 23:59 UTC may spend it again at 00:01. This
is money code; it is deliberately not touched here and needs the owner's call on
which of the two behaviours is intended.

## Checked and clean

- No secrets in the tree. The 64-hex literals are all published test vectors
  from docs.nano.org (`DOCS_SEED`, `DOCS_PUB`, `DOCS_PRIV` in `tests/`, derived
  from the all-but-one-zero seed) plus block hashes, which are public by
  definition. No `.env`, `.pem` or `.key` file is tracked.
- The sibling repository `nano-mcp-public` was checked for the same trap and
  does **not** have it: its `pyproject.toml` already carries an explicit
  `[tool.setuptools.packages.find]` with an `include` list, so its own `audits/`
  directory cannot break it.
- `nano_sdk/` was read in full by the 2026-09-24 audit and has not changed
  since; nothing in this run's diff touches it.

## Not verified here

- The network-marked tests (5 deselected). They need a live node and a key this
  sandbox does not have, so the RPC client's behaviour against the real
  `rpc.nano.to` is unverified by this run.
- Whether the `audits/` directory should ship inside the source distribution at
  all. It is excluded from the wheel here, which is what a user wants; if the
  owner would rather the notes travelled with the sdist, that is a separate
  decision.
