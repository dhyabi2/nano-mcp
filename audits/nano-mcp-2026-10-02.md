## Checked

- `units.py` end to end. The conversions rescale the Decimal exponent rather than multiplying by
  10**30, so they are exact past the default 28-digit context; `nano_to_raw` refuses non-numbers,
  non-finite values, negatives and anything finer than 1 raw, all as `ValueError`. Clean.
- `block.py`'s `_block_bytes`: 32-byte field lengths, the 128-bit balance range, and the big-endian
  16-byte balance encoding. Clean, and it is what finally refuses a float balance — see below.
- `wallet.py`'s send pipeline: the single `account_info` read for balance + frontier +
  representative, both guards before signing, and `_record_send` only after the node accepts the
  block.
- Every amount type a caller can reach `Wallet.send` with, driven through a stub client that
  records each RPC action. That is where the finding is.

## Found and fixed (this PR)

**`check_send` did not check that the amount was an integer count of raw.** It is documented as the
guard that refuses "before anything is signed or published", and `wallet.py`'s own module docstring
says both guards run "before anything is signed or published". Measured, with a stub client holding
0.01 XNO and recording every RPC action:

| `Wallet.send(DEST, amount)` | before | RPC spent |
|---|---|---|
| `nano_to_raw("0.001")` (an int) | published, balance `9000000000000000000000000000` | work_generate, process |
| `1e27` (float raw) | `AttributeError: 'float' object has no attribute 'to_bytes'` | **work_generate** |
| `0.001` (float, XNO by mistake) | `AttributeError: 'float' object has no attribute 'to_bytes'` | **work_generate** |
| `Decimal(10**27)` | `AttributeError: 'decimal.Decimal' object has no attribute 'to_bytes'` | **work_generate** |
| `"1000"` (str, as JSON gives it) | `TypeError: '<=' not supported between 'str' and 'int'` | none |
| `True` | **PUBLISHED a send block**, balance `9999999999999999999999999999` | work_generate, process |

Three distinct problems, one missing check:

1. **A float amount passes the guard.** It is refused eventually, but by
   `balance_raw.to_bytes(16, "big")` in `block.py:50`, as an `AttributeError` — not one of the
   module's documented exceptions, and only *after* a `work_generate` round-trip, which on a keyed
   public node is a billable call. A float cannot hold a raw amount at all: at 10**30 raw to the
   XNO there is no exact binary representation, so it must be refused, not carried.
2. **`True` published a real send of 1 raw.** `bool` is a subclass of `int` and `True > 0`, so it
   passed every guard and `raw_balance - True` became the new balance. `{"amount_raw": true}` in a
   JSON body is all it takes.
3. **A string amount raised `TypeError`** out of the comparison inside `check_send`, where the
   module raises `ValueError` for a bad amount.

Fixed with one check at the top of `check_send`, before `amount_raw <= 0`, raising the `ValueError`
the function already uses for a bad amount, and excluding `bool` explicitly because of (2). It can
only refuse inputs that previously crashed or should never have been accepted; every integer amount
behaves exactly as before, pinned by the existing suite.

Because `check_send` runs before `work_generate`, the refusal now costs no `work_generate` and no
`process`. `send` still reads `account_info` first either way — that is a read, and the new test
says so rather than claiming more.

Tests: 3 new cases in `tests/test_wallet.py`; all 3 fail on `main` and pass with the fix. They
touch no other test file, so this branch does **not** conflict with #10, #11, #12 or #13.

## Found, NOT fixed

1. **`rep = info.get("representative", self.representative)`** (`wallet.py`) uses a `.get` default,
   so a node answer carrying `"representative": null` yields `None` rather than the wallet's
   configured representative — unlike the line above it, `info.get("frontier") or "0" * 64`, which
   handles both. Same for `int(info.get("balance", "0"))` against an explicit null. Not changed:
   no node is known to answer that way, and inventing a fallback inside the send path on a
   hypothetical is worse than reporting it.
2. **`frontier_ascii = frontier_hex.encode()` then `.decode()`** before `work_generate` is a
   no-op round trip. Cosmetic; left alone deliberately — a whitespace-grade change is noise.
3. **`DEFAULT_DAILY_CAP_RAW = int(nano_to_raw("0.01"))`** — `nano_to_raw` already returns `int`.
   Also cosmetic, also left.
