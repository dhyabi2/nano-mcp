## What I found and fixed

**Two independent nodes could name different senders for one block, and the
facilitator published one of them as verified.**

`verify_block_on_independent_endpoints` (`nano_mcp/facilitator.py:340-392`) asks every
configured endpoint for the block and refuses unless each one confirms it, is a send,
carries the exact required amount, and names the required payee. Four fields are
checked against something on every endpoint. The fifth — the payer, `nb.account` — was
not checked against anything. It was read off `confirmed_sends[0]`, whichever endpoint
answered first (`facilitator.py:717` and `:781`), and the other endpoints' readings of
it were discarded.

So two nodes returning the same confirmed send, of the right amount, to the right
payee, but naming different senders, both passed, and the verdict carried the first
one's:

```
VERIFY: {'isValid': True, 'payer': 'nano_1aaaa...', 'extra': {'confirmedOn': 2, 'consulted': 2}}
SETTLE: {'success': True, 'payer': 'nano_1aaaa...', 'amount': '1000000000000000000000000000000'}
```

`nano_1bbbb...` was the sender according to the second endpoint. `confirmedOn: 2` says
two independent nodes confirmed this payment; one node's word is all that stands behind
the sender it names. That is exactly the single-RPC trust this function exists to
remove (strategy law L1, and the README's "at least two independent RPC endpoints").

The same gap had a second mouth: a node that omits `block_account` altogether reads as
`account=""` (`NormalizedBlock`'s own docstring: "may be blank if node omits it ... but
a blank is surfaced"), and that produced an **isValid verdict with `'payer': ''`**.

It matters because the payer is published as fact, not as a hint. `/verify` and
`/settle` both answer it; a resource server binding an entitlement or a refund to the
sender reads it from there; and `evidence.append_nano_tx` writes it into the journal
`scorecard.count_external_receipts` counts from, where it is gated by
`should_log(payer, own_accounts)` — and `""` is in no `NANO_AGENT_OWN_ACCOUNTS` set, so
a blank payer counts as an outside agent having paid us. `should_log("", {PAYER})` is
`True`; there is a test for that in the new file, so the claim is shown rather than
asserted.

**Fix:** two added refusals in the per-endpoint loop, immediately after the payee check
and modelled on it. A blank `nb.account` raises `block_info on <url> carries no payer
account ...`; an `nb.account` that differs from the first endpoint's raises `block is
paid by X on <url> but by Y on <url> ...`. Both are `RpcError`, which the existing
handler already turns into a fail-closed refusal.

It narrows what is accepted and nothing else: no amount, payee, destination, rounding,
proof, claim key or key path is touched, no existing refusal is removed or widened, and
a block every endpoint reads the same way verifies and settles exactly as before. The
refusal also leaves the proof unclaimed, so the sender who really did send it can still
settle — pinned by `test_a_disagreement_does_not_spend_the_claim`.

## Checked and left alone — deliberately

- **`payTo` is compared to the block's payee as an exact string.** Nano's `nano_` and
  `xrb_` spellings name the same account, so a requirement pinned in one form against a
  node quoting the other refuses a payment that was in fact made. It fails safe
  (refuses, never pays or over-credits), and the sibling repositories recorded the same
  call on the same reasoning (`gpt-researcher-x402-retriever`'s 10-12 note on
  `X402_PAY_TO`). Treating an exact pin as exact is defensible, so it is recorded here
  rather than changed: widening what is accepted on a settlement path is a decision,
  not a correction.
- **`NormalizedBlock.is_send` accepts `subtype` `''`.** An empty subtype is read as a
  send. Tightening it would refuse blocks from a node that does not report the subtype,
  and the amount and payee checks already bound what such a block can be credited for.
  No failing path demonstrated.
- **The amount is cross-checked by construction, not by comparison.** Every endpoint's
  `nb.amount_raw` is compared to `expected`, so they cannot disagree without one of
  them refusing. Same for the payee against `pay_to`. That is why the payer was the
  only field with a gap, and why the fix is three lines rather than a rewrite.

  do, not a claim that they have.
