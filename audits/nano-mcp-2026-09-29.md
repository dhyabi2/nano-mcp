# nano-mcp — code audit, 2026-09-29

Scope: the tree at `88756a3` (`main`), offline. Baseline in a clean virtualenv, before any change:

```
$ pip install -e ".[dev]"                  # succeeds
$ python -m pytest -m "not network" -q
64 passed, 5 deselected
```

The three previous audits read `nano_sdk/` line by line and then fuzzed the pure functions. This run
went at the module boundary instead: every public entry point in `__all__` was driven with the
argument *types* a caller can plausibly hold, rather than with well-typed nonsense values. That is
where the defect below came from, and it is the third instance of one shape — a documented contract
answering an undocumented exception.

## Found and fixed (pull request left open)

**A destination that is not a string crashed the wallet's own guard with `TypeError`.**
`public_key_from_address` documents "Raises ValueError if the address is malformed"; `validate_address`
documents a bool and catches only `ValueError`. Both begin with `ADDRESS_RE.match(address)`
(`crypto.py:76`), and `re.match()` raises `TypeError` for anything that is not a string or a
bytes-like object — so neither contract held:

```
validate_address(None)              -> TypeError: expected string or bytes-like object, got 'NoneType'
validate_address(addr.encode())     -> TypeError: cannot use a string pattern on a bytes-like object
validate_address(123)               -> TypeError: expected string or bytes-like object, got 'int'
public_key_from_address(None)       -> TypeError   (documented ValueError)
```

It surfaces one layer up, in the money path. `Wallet.send` validates its destination through this
function (`wallet.py:130`) and raises its own `ValueError("destination is not a valid nano_ address")`
when the check fails. With a non-string destination the check never gets to fail:

```
Wallet.send(None, 1)          -> TypeError: expected string or bytes-like object, got 'NoneType'
Wallet.send(addr.encode(), 1) -> TypeError: cannot use a string pattern on a bytes-like object
```

Neither input is exotic. `None` is what a missing key in a config or a JSON payload
(`{"destination": null}`) hands you, and `bytes` is what `open(path, "rb").read()` and most socket
reads give. A caller that wrote the handler the docstrings ask for — `except ValueError` — does not
catch either, so a mistyped destination escapes as an unrelated exception from inside the regex
module instead of being reported as the bad address it is.

This is the **third** route to the same failure in this one function. The 09-24 audit closed an
`AssertionError` escaping it; the 09-26 audit closed a `KeyError` escaping it (the `$` anchor and a
trailing newline). The remaining route was the argument's type.

**Fixed** by refusing a non-string argument as malformed, with the documented `ValueError`, before the
regex is reached. Nothing else changed; the guard can only refuse inputs that previously crashed.

Proved both directions. Against the unfixed `crypto.py`, with the two new tests in place:

```
FAILED tests/test_crypto.py::test_a_non_string_address_is_refused_not_a_crash
FAILED tests/test_crypto.py::test_the_wallet_guard_reports_a_non_string_destination_as_a_bad_address
E       TypeError: expected string or bytes-like object, got 'NoneType'
nano_sdk/crypto.py:76: TypeError
2 failed, 64 passed, 5 deselected
```

With the fix, in the same venv: **66 passed, 5 deselected**. The second test pins the wallet end of it
with a stub client that raises if any RPC is reached, so it also proves the guard still refuses
*before* the network.

**Not merged.** `crypto.py` is the key path, which the standing instruction for these runs excludes
from self-merging, and the 5 `network`-marked tests could not be run here. Left open for a person.

## Found, not fixed — for a person

**The package declares a dependency on `mcp>=1.0` that nothing in it imports, and the README's repo
layout names a directory that does not exist.** `pyproject.toml` lists `mcp>=1.0` among the runtime
dependencies and describes the distribution as an "MCP server + SDK"; the README's "Repo layout"
lists `nano_mcp/ — MCP server exposing wallet and pay-per-call tools (later blocks)". There is no
`nano_mcp/` directory, and `grep -rn "import mcp\|from mcp" nano_sdk tests` returns nothing. So
everyone who installs this pulls `mcp` and its transitive tree (pydantic, starlette, uvicorn, anyio,
sse-starlette, …) to run a pure-Python SDK that never touches it — a large install for code that is
not here. Whether the answer is to drop the dependency or to ship the server is a release decision, so
nothing was changed.

**Still open from earlier runs, unchanged:** no `LICENSE` and no `license` field, while the public
sibling `dhyabi2/nano-mcp-public` is MIT (reported 09-26); two repositories publishing `nano-mcp`
version `0.1.0` with materially different trees (09-26); `wallet.py:138`
`info.get("representative", self.representative)` versus the sibling's `or` form, which differ when a
node answers with an empty representative (09-26); and the daily cap keyed on the UTC calendar day
(`_today()`, `int(time.time()) // 86400`) while the docstring promises "per day" — a wallet may spend
the full cap at 23:59 and again at 00:01. All four are money or owner decisions. This is the fourth
audit to report the cap.

## Checked and clean

- **No secrets in the tree.** The 64-hex-shaped lines are the published `docs.nano.org`
  all-but-one-zero seed vector and keys derived from it (`tests/test_block.py`, `tests/test_crypto.py`)
  plus two public block hashes in `.ledger/ledger.json`. No `.env`, `.pem`, `.key` or token shape is
  tracked, and nothing of that kind appears in the history a shallow clone carries.
- **Packaging.** `pip install -e ".[dev]"` succeeds and `tests/test_packaging.py` runs the same
  backend hook the installer runs, so `audits/` gaining a fifth file cannot break installation
  silently. `tests/test_repo_tree.py` confirms git ignores `build/` and `dist/` and tracks neither.
- **The README makes no external claims that can 404**: it contains no links at all. Its one unmet
  claim is the `nano_mcp/` layout line above.
- **`RpcClient.call`.** The 09-26 hardening holds: a non-200, a body that is not JSON, a body that is
  not a JSON object, and an object carrying `error` all raise `RpcError` and nothing else escapes.
- **Units.** The documented `ValueError`-only contract holds for every non-numeric type tried
  (`None`, `bytes`, `list`, `""`, `" "`, `"abc"`, `Decimal("NaN")`, `Decimal("Infinity")`); the
  round trip `nano_to_raw(raw_to_nano(x)) == x` holds, and `nano_str` renders `0`, negatives and
  `10**40` raw without an exponent.
- **The address codec** still encodes and decodes every account this library derives, in both `nano_`
  and `xrb_` form — pinned by the existing test and unaffected by the change above.
- `nano-mcp` is still not on PyPI (`pypi.org/pypi/nano-mcp/json` → 404), so no published artefact
  carries any of this.

## Not verified

- The 5 `network`-marked tests. They need the live `rpc.nano.to` node and `NANO_RPC_KEY`, neither of
  which this sandbox has. None of them reaches the changed line.
- The live send path end to end. It needs a funded wallet, and an audit should not be moving money.

an address) were still open at the time of this run, both `mergeable: clean`. Both are `crypto.py`,
both append to the end of `tests/test_crypto.py`, and so does this one — whoever merges them will hit

did; no two of the three touch the same function.
