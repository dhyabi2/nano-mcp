# nano-mcp — code audit, 2026-09-29

Scope: the tree at `88756a3` (`main`). Baseline in a clean virtualenv, before any change:

```
$ pip install -e ".[dev]"                  # succeeds
$ python -m pytest -m "not network" -q
64 passed, 5 deselected
```

Earlier runs read `nano_sdk/` line by line (09-24) and drove the pure functions against their
stated contracts (09-26). Repeating either would have found nothing new, so this run audited the
**distribution** — what a stranger's `pip install` actually fetches and gets — and re-probed the
public API for contract breaks. One new defect, in packaging.

## Found and fixed

**`pyproject.toml` made every installer download the whole MCP server stack for code that is not
in this distribution.** `dependencies` declared `mcp>=1.0`, and nothing under `nano_sdk/` imports
it — the `nano_mcp/` server the dependency exists for is still "later blocks" in the README's own
repo layout. `dependencies` is not documentation: every name in it is resolved, downloaded and
constraint-applied on every install. Measured, same machine, same Python, `pip install -e ".[dev]"`:

```
before:  40 packages, 89 MB of site-packages
after:   16 packages, 48 MB
```

The 24 packages a user was paying for without a line of code to use them include `starlette`,
`uvicorn`, `pydantic`, `pydantic_core`, `cryptography`, `PyJWT`, `jsonschema`, `opentelemetry-api`,
`python-multipart` and `sse-starlette`. Size is the smaller half of the cost: those versions also
become constraints on the environment doing the installing, so an agent pinned elsewhere in that
tree can fail to install an SDK that never touches any of it.

**Fixed** by removing the line, with a comment saying where it goes when `nano_mcp/` ships.
Nothing else in the file changed.

Proved both directions. The new law reads the declared runtime dependencies and the imports
`nano_sdk/` actually makes; against the unfixed `pyproject.toml`:

```
FAILED tests/test_packaging.py::test_every_declared_runtime_dependency_is_imported_by_the_shipped_package
E   AssertionError: pyproject.toml makes every installer fetch these, and nothing
E   under nano_sdk/ imports them: ['mcp'].
```

With the fix, in the same venv: **65 passed, 5 deselected** (64 before). A fresh virtualenv
installs the package, `import nano_sdk` works, `python -m build --wheel` succeeds, and the wheel's
metadata now reads `Requires-Dist: httpx>=0.24` / `ed25519-blake2b-fork>=1.4` and nothing else.
The wheel still carries `nano_sdk` and nothing else, so the 09-25 discovery fix is unaffected.

The law is the point as much as the one-line removal: whoever adds `nano_mcp/` has to add the
import and the dependency together, and a stale declaration cannot drift back unnoticed.

## Found, already raised — not re-raised here

Re-probing the public API reproduced two defects that are **already open pull requests** on this
repository from earlier runs. Both were confirmed live on `main` today; neither is duplicated:

- **#11** — `address_from_public_key` does not check its key length, so a key that is not 32 bytes
  is silently encoded into a confident-looking `nano_` address that fails its own checksum.
  Reproduced: a 33-byte key loses its leading byte and yields
  `nano_41a3161i41a3…iwgshtdf`, for which `validate_address` returns `False`. A caller could
  publish that as a receiving address.
- **#12** — `validate_address` is documented to return a bool and raises `TypeError` for `None`,
  `bytes` or an `int`, because `ADDRESS_RE.match` sees the raw object.

Both are in `crypto.py`. Also still open is **#10** (refuse a private key that is not 32 bytes).

## Found, not fixed — for a person

All three carry over unchanged from 09-26, and are recorded again because nothing has moved:

- **No licence at all.** No `LICENSE`, no `license` field, while the public sibling
  `dhyabi2/nano-mcp-public` carries both and says MIT. A public repository with no licence grants
  a reader no right to use it. Declaring one is the owner's call.
- **Two repositories publish `nano-mcp` `0.1.0` with different code.** This tree has no `nano_mcp/`
  and no `Wallet.receive` / `build_receive_block`; the sibling does. One name, one version, two
  packages, depending on the URL. Which repository is the distribution is a release decision.
- **The daily cap is a UTC calendar-day bucket, not the rolling 24 hours the docstring promises.**
  `Wallet` says "at most 0.01 XNO per day"; `_today()` keys on `int(time.time()) // 86400`, so the
  full cap can be spent at 23:59 UTC and again at 00:01. Money code, untouched. Four audits have
  now reported it.

## Checked and clean

- **No secrets in the tree or in the history a shallow clone carries.** The 64-hex lines are the
  published `docs.nano.org` all-but-one-zero seed vectors in `tests/`, the keys derived from them,
  and two public block hashes in `.ledger/ledger.json`. No `.env`, `.pem`, `.key`, no token shapes,
  no private-key blocks.
- **Packaging, end to end.** Build-backend hook, `pip install -e ".[dev]"`, `python -m build
  --wheel`, wheel contents and wheel metadata all verified after the change, in a virtualenv
  created for this run.
- **The README** makes no external claims that can rot: it contains no links, and it is honest
  that `nano_mcp/` is future work — which is exactly why the dependency did not belong in the
  install.
- **Unit conversions and the address codec** behave as the 09-26 run recorded; re-probed with the
  same shapes plus `float`, `bool`, `None` and `"-0"` inputs, and found no new contract break
  beyond the two already-open ones above.
- `nano-mcp` is still not on PyPI (`pypi.org/pypi/nano-mcp/json` → 404), so no published artefact
  carries the heavy dependency list. This fix lands before a release rather than after one.

## Not verified

- The 5 `network`-marked tests. They reach the live `rpc.nano.to` node and need `NANO_RPC_KEY`,
  which this sandbox has neither of. Nothing in this change is reachable from them — it touches no
  Python that runs, only the dependency list — and the offline suite passes in full.
- The live send path. It needs a funded wallet, and an audit should not be moving money.
