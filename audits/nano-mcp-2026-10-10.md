## Found and fixed (this PR)

**A malformed `requirements` crashed `/verify` and `/settle` instead of refusing them** —
`nano_mcp/facilitator.py:518` (`_check_requirements`), reached from `verify()` at line 441 and
`settle()` at line 486.

`REQUIRED_SECTIONS` (line 396) listed the mandatory fields and was **never read by anything**.
What `_check_requirements` actually did was compare `requirements` against the payload's
`accepted` block — so a field missing from *both* halves is `None == None` and passed every
check. `verify` and `settle` then indexed `requirements["payTo"]` and `requirements["amount"]`
directly, and `verify_block_on_independent_endpoints` called `parse_raw(amount)` at line 265,
outside any `try`. Neither exception is caught anywhere above `make_handler`'s `do_POST`, which
only guards the JSON read.

Driven against the real `Facilitator` with two stub endpoints that fail the test if consulted:

| `requirements` | before | after |
|---|---|---|
| no `payTo`, no `payTo` in `accepted` | `KeyError: 'payTo'` | `isValid: false`, `bad-requirements` |
| no `amount` either side | `KeyError: 'payTo'` | `isValid: false`, `bad-requirements` |
| `amount: "abc"` | `ValueError: invalid literal for int()` | `isValid: false`, `bad-amount` |
| `amount: "1e30"` | `ValueError: invalid literal for int()` | `isValid: false`, `bad-amount` |
| `amount: ""` | parsed to **0**, both nodes consulted | `isValid: false`, `bad-amount` |
| `amount: "-1"` | parsed to **-1**, both nodes consulted | `isValid: false`, `bad-amount` |
| `requirements: []` | `AttributeError: 'list' object has no attribute 'get'` | `isValid: false`, `bad-request` |

And as a client actually sees it, over the HTTP surface `serve()` builds — a POST to `/verify`
and to `/settle` with `payTo` absent:

```
/verify -> RemoteDisconnected: Remote end closed connection without response
/settle -> RemoteDisconnected: Remote end closed connection without response
```

with `KeyError: 'payTo'` on the server's stderr. A paying agent cannot tell that apart from the
facilitator being down: the x402 contract says a refusal arrives as
`{"isValid": false, "invalidReason": ...}`, and here no body arrived at all. After the fix both
answer `HTTP 200` with that JSON refusal.

**The fix adds refusals only.** `_check_requirements` now, *after* every check it already made
and in that unchanged order (so no existing `invalidReason` string moves):

* refuses a `requirements` or `payload` that is not a JSON object, and an `accepted` that is not
  one — `bad-request`;
* finally enforces `REQUIRED_SECTIONS`: any of `scheme`, `network`, `amount`, `asset`, `payTo`
  absent or blank is `bad-requirements`;
* parses `amount` once through `parse_raw` and refuses what it cannot read, or what is not
  positive — `bad-amount`.

No amount, destination, rounding or key path is touched. `parse_raw` still reads the decimal-XNO
form it always did, so nothing that could be quoted before is refused now; the three
well-formed-amount controls below prove that directly.

**Evidence.** 21 new laws in `tests/test_facilitator_refuses_malformed_requirements.py`. With
`tests/` kept and `nano_mcp/` alone reverted to `main`: **18 failed, 3 passed** — the 3 are the
controls (`0.000001`, `1`, `1000000000000000000000000000000` raw) that must still reach the
nodes and be refused as `unconfirmed`, and they hold either way. With the fix: **21 passed**,
full suite **249 passed, 11 skipped, 1 failed** (the same live-price-API failure as the
baseline). Each of the three guards was mutation-checked independently — `if False:` on the
missing-fields refusal fails 7 of them, on the non-positive-amount refusal 4, on the
`isinstance` guard 1 — and the tree was restored byte-for-byte after each and the suite re-run.

One note on writing these tests: a stub endpoint that *raises* when consulted proves nothing
here, because `verify_block_on_independent_endpoints` catches every endpoint exception itself
(line 311, `except Exception`) and turns it into `unconfirmed`. The first draft of the control
test did exactly that and silently passed against the unfixed code. The committed version
records the calls instead and asserts both nodes saw the proof hash.

## Found, NOT fixed here

**`build_fail_closed_config` will accept the same node twice as "two independent endpoints"** —
`nano_mcp/facilitator.py:323-329`. `if custom and len(custom) >= 2: return list(custom)` counts
entries, never distinct URLs, and `verify_block_on_independent_endpoints` then reports
`consulted: 2`. A self-hoster passing `[RpcEndpoint("https://rpc.nano.to"),
RpcEndpoint("https://rpc.nano.to")]` gets a verdict decided by one node while the result says
two agreed — which is the single-RPC outage, or single-RPC lie, that strategy law L1 exists to
refuse. Left out of this PR under one-concern-per-branch; the fix is a refusal (or a dedupe of
the URL set) and is in scope for a routine to land on its own branch.

**`NormalizedBlock.is_send` returns True for an unknown subtype** — line 99,
`self.subtype in ("send", "state", "")`. The `""` arm fails *open*: a node that returns neither
a top-level `subtype` nor a `contents.type` yields `""` and the block is treated as a send. The
`"state"` arm is nearly as loose, since every modern Nano block — receive, change and epoch
included — has `contents.type == "state"`, and that is the value reached whenever the top-level
`subtype` is absent. What stops this being exploitable today is the payee check immediately
below: a receive block's `link_as_account` is derived from the send block's hash, and a change
or epoch block's is the burn address, so neither can equal a `payTo`. I could not construct a
block that passes the payee check and should not be a send, so this is recorded as a loose
guard rather than a proven defect, and nothing is changed on that basis.

## Checked and clean

* **`verify_payment`'s quote floor still holds.** `service.py:215-217` checks the **higher** of
  the amount its caller names and `store.quote_price(request_id)`, and
  `store.record_quote_price` (line 131) takes `max(existing, new)` so a re-quote — including
  `pay_and_call`'s, which re-quotes at an amount its own caller names — can only raise it.
  Re-read both paths against the 2026-10-08 attack table; neither is reachable now.
* **The `verify_payment` tool still has no `require_onchain` argument** (`server.py:129`), so
  the `tx_hash: "simulated"` approval is not reachable from the surface a payer talks to.
* **Integer raw end to end.** `nano_sdk/units.py` converts by rebuilding the Decimal exponent
  (`_rescale`), exact and context-free; `nano_to_raw` refuses >30 decimal places, non-finite and
  negative amounts. `grep` for `float(`/`parseFloat`/`toFixed`/`1e30` over `nano_mcp/` and
  `nano_sdk/` finds no float on an amount anywhere.
* **`settle` re-runs the full verification** rather than trusting a prior `/verify`
  (`facilitator.py:485`), and the single-use claim is an atomic `INSERT … PRIMARY KEY` keyed by
  `nano:live <hash> <request_id>` with a rollback on conflict.
* **The payee is read and compared, never assumed.** `normalize_block_info` reads
  `contents.link_as_account` (the field a real state block actually carries), and an unreadable
  payee is a refusal, not a default to `pay_to` (lines 289-297).
* **No secret in the tree or history.** The master secret comes from
  `NANO_PAYMENT_MASTER_SECRET`; `git log --all -p` grepped for `nano_`/`xrb_` seeds, 64-hex
  blobs, `sk-`, `ghp_`, `AKIA`, JWT and PEM headers — nothing. `Wallet.seed` is still
  `field(repr=False)` and `Account.__repr__` still withholds the private key.
* **A new agent's first step runs.** `pip install -e ".[dev]"` succeeds from a clean clone, the
  `nano-mcp` console script is declared (`pyproject.toml`), and `tests/test_packaging.py` and
  `tests/test_directory_handshake.py` hold both.

## Could not verify

* **No live node and no live payment.** This environment's network policy reaches neither
  `rpc.nano.to` nor the three price APIs, so every result above is measured against the
  repository's stubs and its recorded real-node shapes
  (`tests/test_facilitator_real_node_shape.py`). No XNO moved.
* **Whether a facilitator has crashed this way in production** is not knowable from here. What
  is shown is that the crash is reachable from the documented HTTP surface with a well-formed
  JSON body.
* **`_onchain_paid` does not look at a per-entry `confirmed` flag** (`service.py:142-168`); it
  trusts that `account_history` lists settled chain state. Whether a given node can return an
  unconfirmed entry there could not be established without a live node, so nothing was changed
  on that basis.
